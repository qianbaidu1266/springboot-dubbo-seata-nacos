### 结论：顺序是强制的（默认配置下）
1. account / storage（可并行，无下游）
2. order（依赖 account）
3. business（依赖 order + storage）

原因：代码里写的是 `@DubboReference(version = "1.0.0")`，**没有 check=false**。
反射读取确认 dubbo 2.7.13 的 `@DubboReference#check` 注解默认值 = **true**。

### 验证方法（可复用）
用 `samples-order/target/samples-order-1.0.0.jar`（90MB fat jar）解出 `BOOT-INF/lib/*.jar` 作为 classpath，
写一个不依赖 Spring/MySQL 的 `ReferenceConfig` 探针指向 `nacos://127.0.0.1:8848`：
- `check=true` + 无提供者 → `IllegalStateException: Failed to check the status of the service ...AccountDubboService. No provider available for the service ...:1.0.0`（约 1253ms）
- `check=false` → 约 1164ms 正常拿到代理
放在 Spring Boot 里该异常抛在 `ReferenceBean.getObject()`，会让 context refresh 失败 → **应用直接起不来**，
不是"起来了但调用报错"。

### 想解除顺序依赖（可选，尚未落地）
- 逐处改：business 的 2 个 + order 的 1 个 `@DubboReference` 加 `check = false`
- 或全局：business/order 的 yml 加 `dubbo.consumer.check: false`
注意 check=false 只跳过启动校验，调用时提供者仍缺失依然会失败（错误推迟到调用期）。

### 环境依赖（顺序之外，优先级更高）
- **Nacos 8848 必须先起**：4 个服务都靠它做 Dubbo 注册 + Seata 注册/配置
- seata-server TC 8091：不在也能启动，但一调 `/business/dubbo/buy` 就找不到 TC
- **MySQL 3306 + 库 `seata_demo`**：建库脚本 `sql/db-seata.sql`，含 t_account / t_order / t_storage / **undo_log**（AT 模式必需）
- 当前状态（2026-09-11 00:1x）：Nacos ✅、seata-server(8091) ✅、MySQL ❌（3306 无监听）、四个业务服务 ❌ 均未启动

### 顺带发现的死配置
business / order 的 yml 里有 `dubbo.consumer.provided-by: dubbo-xxx-example`，
但 dubbo 2.7.13 的 `ConsumerConfig` / `AbstractInterfaceConfig` / `AbstractReferenceConfig` 里

## 【已修复】TC 注册 198.18.0.1 → 导致 account/storage 启动失败

> 本节的结论**覆盖**上面"关键结论"第 7 条（那条描述的是修复前的状态）。

### 现象
account / storage 启动即挂，`globalTransactionScanner` 初始化失败：
- VPN 开：`can not register RM,err:register TMROLE error, errMsg:null ,cost: 30012 ms` → `can not connect to [198.18.0.1:8091]`
- VPN 关：`connect failed, can not connect to services-server`（10s，`NettyClientBootstrap.getNewChannel`）

### 根因（读字节码 + 实测，非推测）
1. `seata-server/conf/application.yml` 的 `preferred-networks: 192.168.43.*` 已失效
   ——本机 en0 现在是 **192.168.5.3**。历史日志佐证：9/3、9/4 正常时 xid 前缀是 `192.168.43.156:8091`。
2. `NetUtil.getLocalAddress0` 逻辑：跳过回环 → **先记下"第一个合法地址"当兜底** → 有 preferred 就匹配、命中即返回
   → 全不匹配则打 `Could not match ip by preferredNetworks:{} , will use default first ip {} instead.` 并**回退用兜底**。
3. **macOS 上 Java 枚举网卡是按下标倒序的**（实测：utun3(21)→utun2(20)→utun1(19)→utun0(18)→llw0(17)→awdl0(16)→en0(14)→lo0(1)）。
   代理的 `utun4`(index=22, 198.18.0.1) **永远排在 en0 前面** → 兜底选中 198.18.0.1。
4. 排除项：`127.0.0.1` 在扫描阶段就被 `isValidAddress` 过滤（`FORBIDDEN_HOSTS` + `isLoopbackAddress`），
   所以 `preferred-networks: 127.0.0.1` 写不进。

### 关 VPN 为什么没用
Nacos 里那条实例是 TC 注册的**临时实例**，靠 TC 自身心跳续命，Nacos 从不校验 IP 是否真实存在。
关掉 VPN 只是让 utun4 消失，注册记录还在 → 客户端改为直接连不上（10s 失败）。

### 修复（已执行并验证）
`seata-server/conf/application.yml`：`preferred-networks: 192.168.43.*` → **`192.168.*`**
（备份：`conf/application.yml.bak-20260911-002910`；已 kill 旧 TC PID 20289 并用 JDK 17 重启，新 PID 39650）

验证链：
- TC 日志：`Starting ServerApplication v2.6.0 using Java 17.0.12 on 192.168.5.3`
- Nacos：`ip=192.168.5.3 port=8091 healthy=true`（旧的 198.18.0.1 条目已消失）
- account 服务实测：`will connect to 192.168.5.3:8091` → `register TM success 89ms` → `register RM success 7ms`
  → `Started AccountExampleApplication in 5.215 seconds`（Tomcat 8102）**启动成功**

选 `192.168.*` 而不是 `192.168.5.*` 的理由：即使 utun4 排在最前也不匹配，扫描继续到 en0 命中即返回，
**顺序敏感被消除，VPN 开着也能正常注册**。

### 客户端侧（实测结论）
给样例服务加 `-Dseata.registry.preferred-networks=10.99.*` 后，既不打印 `Could not match ip` 警告，

## 【重要结论】Dubbo 2.7.13 就支持 tag 路由，无需升 3

用户最初以为"tag 是 3.0+ 才有"，**实测证伪**。证据（读 `~/.m2` 里 2.7.13 各 jar + 跑探针）：

1. `dubbo-cluster-2.7.13.jar` 内有 `TagRouter` / `TagRouterFactory`，`TagRouterFactory` 标注
   `@Activate(order=100)` → **默认挂在 RouterChain 上**，不需要额外开启。
2. `AbstractInterfaceConfig` 有 `protected String tag`，`getTag()` 标注
   `@Parameter(key="dubbo.tag", useKeyAsProperty=false)`。
3. `@DubboService` / `@DubboReference`（以及旧的 `@Service` / `@Reference`）都带 `tag()` 属性。
4. `rpc/filter/ContextFilter` 把 `dubbo.tag` / `dubbo.force.tag` 放进 invocation attachment。
5. **实测探针**（用 samples-order fat jar 的 BOOT-INF/lib 做 classpath）：
   `ProviderConfig.setTag("gray")` → URL 参数 `{deprecated=false, dynamic=true, dubbo.tag=gray}`
   `ConsumerConfig.setTag("gray")` → URL 参数 `{sticky=false, dubbo.tag=gray}`
   未设 tag → 无 `dubbo.tag` 参数。**即 `dubbo.provider.tag` / `dubbo.consumer.tag` 直接映射到 `dubbo.tag`。**

### TagRouter.filterUsingStaticTag 的路由语义（读字节码）
- consumer **有** tag=T：先找 provider 中 `dubbo.tag==T` 的
  - 找到 → 只路由到它们（隔离达成）
  - 没找到 → 若 `dubbo.force.tag!=true`（默认 false）→ **回退到"所有无 tag 的 provider"**；
    若 force=true → 返回空 → `No provider available`
- consumer **无** tag：**只保留"无 tag 的 provider"** → 会自动排除所有打标 provider
- ⚠️ **陷阱：必须成对打标**。只给 provider 打 tag、consumer 不打 tag，consumer 会看不到这些 provider，
  直接 `No provider available`（因为无 tag 的 consumer 只认无 tag 的 provider）。
- 严格隔离可加 `dubbo.consumer.parameters."dubbo.force.tag"=true`（TagRouter 的 `url` 是消费端 URL）。

### XID 透传机制（升级评估的关键）
- **不是** Seata 官方模块，而是 **`org.apache.dubbo.extensions:dubbo-filter-seata`**，
  由 **`seata-all:2.6.0` 传递引入**（seata-all 的 pom 里显式声明 1.0.2，排除 seata-core）。
- SPI：`META-INF/dubbo/org.apache.dubbo.rpc.Filter`
  → `seata-provider=org.apache.dubbo.seata.SeataTransactionPropagationProviderFilter`
  → `seata-consumer=org.apache.dubbo.seata.SeataTransactionPropagationConsumerFilter`
- **1.0.2 引用的是 Seata 1.x 的 `io/seata/core/context/RootContext`**，
  而 **Seata 2.6.0 特意保留了 `io.seata` 兼容包**（jar 内 193 个 `io/seata/` 条目），所以能跑通。
- 官方 SPI Extensions 页标注 `dubbo-filter-seata` 适配 **2.7.x ~ 3.x.x**；
  Maven 上还有 3.2.0 / 3.3.0 / 3.3.1 等 Dubbo3 线版本。

### Dubbo 3 升级要求（官方文档，2026-09 检索）
| 项 | 要求 | 本项目现状 | 结论 |
|---|---|---|---|

- 改动前备份：`.workbuddy/backup-dubbo3/`。

### 三个关键踩坑（已在 问题记录.md #002 + 手册 §9 详录）
1. **netty 胖包**：`netty-all` 自 4.1.91 起是"空壳聚合器"（0 类），而 4.1.42 是 2667 类的胖包，会与子模块重复类。
   取 Dubbo3.3.6(声明 4.2.2) 与 Seata2.6.0(声明 4.1.101) 交集 → 4.1.101；已核实 Dubbo 3.3.6 不用任何 netty 4.2 独有 API。**不可回退到 4.1.91 以下**。
2. **`dubbo.force.tag` 方括号写法不生效**：`"[dubbo.force.tag]": "true"` 绑不进去（`parameters` 定义在 `AbstractMethodConfig` 上，Dubbo 绑定器不展开括号 key），
   必须写点号 `dubbo.force.tag: "true"`；验证看**消费端 URL** 是否出现该参数（只看 yml 会被骗）。
3. **启动失败晚 30 秒**：Dubbo 3 把消费端校验挪到 `onContextRefreshedEvent`（Spring refresh **之后**）
   → `DefaultModuleDeployer.checkReferences()` → `SimpleReferenceCache.check` → `ReferenceConfig.checkInvokerAvailable(timeout)`，
   **每 100ms 轮询、默认 30000ms** 超时后才抛 `IllegalStateException`。
   超时项 `dubbo.module.check-reference-timeout`（毫秒，默认 30000；设 0 = 立即失败）。
   ⚠️ 中途会打印 `Referred dubbo service` / `Migrated to APPLICATION_FIRST mode` / `Dubbo Application … is ready`，**别当成启动成功**。

### 概念澄清：yml 里的 127.0.0.1 ≠ Nacos 里注册的 IP（用户提问引出）
用户质疑"全是本机服务、配置写的都是 127.0.0.1，为何还受 IP 变化影响"。结论（已写进手册 §4.1 顶部警示块）：
- **两个不同语义的 IP**：yml 的 `nacos://127.0.0.1:8848` 是"去哪注册"（Nacos 服务端地址，客户端连出去）；
  Nacos 实例记录里的 IP 是"注册成什么"（自报家门地址，**配置里根本没写**，框架启动时探测网卡得来）。
- 消费者**不用自己的 127.0.0.1 去连提供者**，而是从 Nacos 取回提供者自报的地址再连 → 所以同机也走真实网卡 IP。
- 框架**在网卡扫描阶段就剔除回环**（字节码证据）：Seata `NetUtil.isValidAddress` 首行 `isLoopbackAddress()` → return false；
  Dubbo `NetUtils` 把 `127.` / `127.0.0.1` / `0.0.0.0` / `localhost` 列入 invalid local host，遍历网卡时 `NetworkInterface.isLoopback()` 跳过。
- **不能靠"强制 127.0.0.1"一劳永逸**：Dubbo 侧有 `dubbo.protocol.host`（`ProtocolConfig` 真实字段）可强指；
  但 Seata 侧不行——`seata-all-2.6.0` 的 `NetUtil` 全类搜不到 `register-ip` / `host` 直配项，只有 `preferred-networks`，
  且回环在匹配前就被剔除，`preferred-networks: 127.*` 永远匹配不上。两边改不齐 → 仍会被 IP 漂移打断，故选择"不强制、换网后重启"。
