# 学习指南：9 步代码走读路线

> 项目：Spring Boot + Dubbo + Seata + Nacos 分布式事务示例（samples-business / samples-order / samples-storage / samples-account / samples-common）
> 目标：快速掌握"一笔下单请求如何贯穿 4 个微服务，并由 Seata 保证分布式事务一致性"
> 用时参考：约 3 小时（阶段 A ≈30 分钟，阶段 B ≈1.5 小时，阶段 C ≈1 小时 + 动手验证）
> 前提：已能跑通环境（Nacos、Seata Server、MySQL + `sql/seata-demo-tcc.sql`、4 个微服务）。本文全部锚点以工作区实际代码为准，与 README.md 的旧版说明无关。
>
> ⚠️ **2026-09-11 更新：本项目已由 AT 模式整体改造为 TCC 模式。**
> 本文正文的走读锚点写于 AT 时期 —— 其中 `*DubboService` / `*DubboServiceImpl` 已被
> `StorageTccAction` / `AccountTccAction` / `OrderTccAction` 及其 `*TccActionImpl` 取代，

> **改造后的走读锚点请看 [TCC改造说明与实测验证.md](./TCC改造说明与实测验证.md) §三 / §四 / §五。**

## 1. 两条测试请求（一切从这里开始）

项目根目录 `test.http` 已预置两条 POST，入参一致，差异只在触发的业务方法：

```http
### 正常流程：三库各扣一笔，全部提交
POST http://localhost:8104/business/dubbo/buy

### 异常流程：故意抛 RuntimeException，观察全量回滚
POST http://localhost:8104/business/dubbo/buy2

# 公共入参
# {"userId":1, "commodityCode":"C201901140001", "count":50, "amount":"100"}
```

| 字段 | 值 | 含义 |
|---|---|---|
| userId | 1 | t_account 表主键 |
| commodityCode | C201901140001 | t_storage / t_order 关联的商品 |
| count | 50 | 下单数量（扣库存、落订单都用它） |
| amount | 100 | 订单金额（扣余额用） |

## 2. 项目全貌：一次请求的调用链

```
HTTP POST /business/dubbo/buy  (:8104, business 服务)
   │
   ▼
BusinessController ────────────► BusinessServiceImpl.handleBusiness()
   │                                   │  @GlobalTransactional  ← 全局事务根（XID 在此产生）
   │                                   │
   │        ┌──────────────────────────┼───────────────────────────┐
   │        │ Dubbo RPC（XID 随调用自动透传）│                           │
   │        ▼                            ▼                           │
   │   storage 扣库存                order 建订单                     │
   │   StorageDubboServiceImpl      OrderDubboServiceImpl            │
   │   → TStorageServiceImpl        → TOrderServiceImpl             │
   │   → UPDATE t_storage           → INSERT t_order                │
   │                                      │  Dubbo RPC（嵌套调用）    │
   │                                      ▼                          │
   │                                 account 扣余额                  │
   │                                 AccountDubboServiceImpl        │
   │                                 → TAccountServiceImpl          │
   │                                 → UPDATE t_account             │
   └─────────────────────────────────────────────────────────────────┘
              三个库各写一笔，任何一处失败 → 全部回滚
```

- **storage / order / account** 三个服务各连一个库、各改一张表；
- **business** 无库、纯编排，是全局事务的唯一发起方；
- 三个数据源都会被 Seata 自动包装成 AT 代理，SQL 写入时自动在 `undo_log` 留前后镜像。

## 3. 总原则：跟"一笔请求"走，不要按模块翻

> 不要从 `samples-common` 目录从头读到尾（会困死在 DTO 里）；不要按 account → order → storage 的模块顺序平铺。
> 正确姿势：顺着 `入口 → 编排 → 分支 → 收网` 的数据流纵向走一遍，只需要精读约 10 个文件。

9 步路线一句话版：

```
①test.http → ②BusinessController → ③BusinessServiceImpl(事务根)
   → ④common 契约 → ⑤storage 分支 → ⑥order 分支 → ⑦account 分支
   → ⑧收网(数据源代理/undo_log) → ⑨动手验证回滚
```

## 5. 阶段 B：下钻三个分支 —— 每个服务内部怎么改库（约 1.5 小时）

三个分支**代码结构完全同构**：Dubbo 接口（common）→ `@DubboService` 实现（本服务）→ `T*ServiceImpl` 业务实现 → Mapper SQL。**精读 ⑤ 即可掌握套路，⑥⑦ 只看差异。**

| 步 | 打开文件 | 看点 | 灵魂问题 |
|---|---|---|---|
| ④ | `samples-common/.../dubbo/` 下 `StorageDubboService` / `OrderDubboService` / `AccountDubboService` + `dto/` 下 4 个 DTO | 三个接口各只有 **1 个方法、无任何注解**；DTO 只是纯数据载体 | 接口为什么放在 common？谁暴露、谁消费？ |
| ⑤ | `StorageDubboServiceImpl` → `TStorageServiceImpl` → `TStorageMapper.xml` | DubboImpl 用 `@DubboService` 暴露并打 XID 日志；`TStorageServiceImpl` 执行 SQL 后**失败只返回 FAIL、不抛异常**；XML 里是条件 UPDATE | XID 怎么"看不见地"跨服务传递？失败为什么不抛异常？ |
| ⑥ | `OrderDubboServiceImpl` → `TOrderServiceImpl`（**内部再调 account**） | 唯一**嵌套链路**：建订单的同时触发扣余额 | 内层失败时，最外层事务根如何感知？ |
| ⑦ | `AccountDubboServiceImpl` → `TAccountServiceImpl` → `TAccountMapper.xml` | 与 ⑤ 完全同构，确认"套路"成立 | 三个分支的代码差异只有表名 / SQL 吗？ |

⑤ 的套路模板（以 storage 为例，`TStorageServiceImpl.java`）：

```java
// L23-35  T 系列实现的统一写法：执行 SQL → 按影响行数返回 SUCCESS / FAIL
public ObjectResponse decreaseStorage(CommodityDTO commodityDTO) {
    int storage = baseMapper.decreaseStorage(commodityDTO.getCommodityCode(), commodityDTO.getCount());
    ObjectResponse<Object> response = new ObjectResponse<>();
    if (storage > 0) {                       // 影响行数 > 0 才算成功
        response.setStatus(RspStatusEnum.SUCCESS.getCode());
        ...
        return response;
    }
    response.setStatus(RspStatusEnum.FAIL.getCode());   // 失败只改状态码
    ...
    return response;
}
```

### 阶段 B 的 aha 时刻（本项目最值钱的设计）

> 三个 `T*ServiceImpl` 失败时**只返回 status，不抛异常** → Seata 的全局事务拦截器**感知不到业务失败**。
> 因此必须由门面层（阶段 A 的 ③，`BusinessServiceImpl` L57-59）把"非 200"翻译成 `DefaultException` 抛出，
> `@GlobalTransactional` 才会触发全局回滚。
>
> **这是以后自己集成分布式事务时最容易踩的坑**：分支方法吞掉异常只回状态码，会导致"部分成功、部分失败"且无回滚。

对应 Mapper SQL（三张表的实际 DML，注意示例用 `${}` 拼接，仅教学演示，生产应改 `#{}`）：

```xml
<!-- TStorageMapper.xml L21-23 -->
<update id="decreaseStorage">
    update t_storage set count = count-${count} where commodity_code = #{commodityCode}
</update>

<!-- TAccountMapper.xml L19-21 -->
<update id="decreaseAccount">
    update t_account set amount = amount-${amount} where user_id = #{userId}
</update>

<!-- TOrderMapper.xml L23-26 -->
<insert id="createOrder" keyProperty="id" useGeneratedKeys="true" ...>
    insert into t_order values(null,#{order.orderNo},#{order.userId},#{order.commodityCode},${order.count},${order.amount})
</insert>
```

## 6. 阶段 C：收网 —— Seata 靠什么兑现"全成或全滚"（约 1 小时）

| 步 | 打开文件 | 看点 |
|---|---|---|
| ⑧ | 各服务 `application.yml` 的 `seata:` 配置段 + `sql/seata-demo-tcc.sql` | TCC 改造后 RM 侧 `enable-auto-data-source-proxy: **false**`（TCC 不走 AT 数据源代理）；yml 只配"如何连 TC、属于哪个事务分组"。**判据改用 `frozen` / `tcc_transaction_control` 是否变化 —— 别再拿 `undo_log` 判断模式**（TCC 下这张表已删除） |
| ⑨ | 按 `test.http` 实际发两遍请求，验证（见下方步骤） | 用结果反向印证前 8 步的机制理解 |

⑨ 的验证操作：

1. **先发 `/buy`（正常）**：business 日志出现 `XID = 192.168.x.x:8091:...`；order/storage/account 三个服务日志出现**同一个 XID** → 证明 Dubbo 透传生效；三个库的表各减一笔。
2. **再发 `/buy2`（异常）**：日志出现 `测试抛异常后，分布式事务回滚！` → 观察三张表数据**全部还原**。
3. **查 `undo_log`**：事务执行期间该表出现带 before_image / after_image 的记录，回滚后消失或标记完成 → 前后镜像是回滚的依据。
