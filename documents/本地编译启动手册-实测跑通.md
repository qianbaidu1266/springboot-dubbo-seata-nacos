# 本地编译启动手册（实测跑通版）

> 适用范围：Spring Boot 2.2.2 + Dubbo 2.7.13 + Seata 2.6.0 + Nacos 2.4.3 的分布式事务示例工程。
> 本文档全部命令与配置均已在本机（macOS arm64）实测跑通：`buy`（正常提交）与 `buy2`（异常回滚）验证通过。
> 全程未改动 MySQL（仅只读确认数据）。

## 2. 编译（JDK 8）

```bash
export JAVA_HOME=~/javatools/jdk8
export PATH=$JAVA_HOME/bin:$PATH
cd <工程根目录>
mvn clean package -DskipTests
# 结果：BUILD SUCCESS；4 个 samples 均产出可执行 jar
```

> 注意：样例服务是 JDK 8 字节码；若用高版本 JDK 编译后回 JDK 8 跑，可能因 class 版本不兼容启动失败，编译与运行请保持一致用 JDK 8。

## 3. 前置：Nacos 侧 Seata 配置（SEATA_GROUP）

Seata 2.x 客户端按 `service.vgroupMapping.<事务组>=<集群名>` 找 TC 集群，配置项存在 Nacos `SEATA_GROUP` 中，**必须用 camelCase**（`vgroupMapping`），1.x 的下划线版 `vgroup_mapping` 不生效。

4 个服务各自的事务组 → 全部映射到默认集群 `default`：

```text
service.vgroupMapping.business-service-seata-service-group = default
service.vgroupMapping.order-service-seata-service-group    = default
service.vgroupMapping.account-service-seata-service-group  = default
service.vgroupMapping.storage-service-seata-service-group  = default
```

可用 Nacos HTTP API 增删查（127.0.0.1:8848）：

```bash
curl -X POST 'http://127.0.0.1:8848/nacos/v1/cs/configs' \
  -d 'dataId=service.vgroupMapping.business-service-seata-service-group' \
  -d 'group=SEATA_GROUP' -d 'content=default'
```

## 4. 启动 Seata Server（TC）——最容易踩坑的一步

### 4.1 前置：确认 TC 注册 IP 正确

TC 会把本机一个网卡 IP 注册到 Nacos，样例服务靠它连 TC。若注册到虚拟网卡（如代理软件 xray 的 utun4 `172.18.0.1`），客户端连不上或时通时断。

编辑 `seata-server/conf/application.yml` 的 registry 段，指定本机真实网段：

```yaml
registry:
  type: nacos
  preferred-networks: 192.168.43.*   # ← 关键：填本机真实 Wi-Fi/有线网段
  nacos:
    server-addr: 127.0.0.1:8848
    group: SEATA_GROUP
    cluster: default
```

查看本机 IP：`ipconfig getifaddr en0`（macOS）。改前先备份：`cp conf/application.yml /tmp/application.yml.bak`.

### 4.2 启动命令（两个硬性要求）

- **JDK 必须 9+（实测 17）**：Seata 2.6.0 server 字节码引用了 JDK 9+ 的 `ByteBuffer.clear()` 协变返回 API，用 JDK 8 跑会在 `GlobalSession.encode` 抛 `NoSuchMethodError`，TC 吞异常不回包，客户端表现为 `GlobalBeginRequest ... RPC timeout` 30s。
- **必须 `-Dloader.path`**：seata-server.jar 是 Spring Boot PropertiesLauncher，不带该参数会 `NoClassDefFoundError: org/springframework/boot/SpringApplication`。

```bash
cd /Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server

/Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home/bin/java \
  -Dlog.home=/Users/yangchao/logs/seata \
  -Dloader.path=/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/lib \
  -Dspring.config.additional-location=/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/conf/ \
  -Dspring.config.location=/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/conf/application.yml \
  -jar target/seata-server.jar
```

启动成功标志（日志）：

```text
Server started, service listen port: 8091
```

并在 Nacos 服务列表出现 `serverAddr=192.168.43.156:8091`（healthy=true）的服务实例（服务名 `seata-server`）。

> 注意：不要在沙箱/托管环境用 `nohup ... &` 起长驻进程（会被回收），用终端前台或任务托管方式运行。

## 5. 启动 4 个样例服务（顺序有讲究）

**先 storage / account / order，最后 business**。business 是门面，启动时若 order/storage 的 Dubbo provider 尚未就绪，会报 `No provider available for OrderDubboService` 启动失败——此时等 order 完全起来后单独重启 business 即可。

每个服务相同姿势（以 storage 为例，其余换目录）：

```bash
cd samples-storage
export JAVA_HOME=~/javatools/jdk8
nohup $JAVA_HOME/bin/java -jar target/*.jar > /tmp/log-storage.log 2>&1 &
```

全部就绪标志（每服务日志都会出现）：

```text
register TM success      # TM 注册到 TC 192.168.43.156:8091
register RM success
```

4 个服务 HTTP 端口 curl 返回 404 属正常（说明 Tomcat 起来了，只是没有映射根路径的 controller）。

## 6. 验证分布式事务

### 6.1 正常提交 buy

```bash
curl -s -X POST http://127.0.0.1:8104/business/dubbo/buy \
  -H 'Content-Type: application/json' \
  -d '{"userId":1,"commodityCode":"C201901140001","name":"fan","count":50,"amount":"100"}'
# 期望：{"status":200,"message":"成功","data":null}（约 1~2s 返回）
```

TC 日志应出现：`GlobalBeginResponse{resultCode=Success}` → 3 条 `BranchCommitResponse{... PhaseTwo_Committed}`（storage/account/order 各一）→ `Committing global transaction is successfully done`。

### 6.2 异常回滚 buy2

```bash
curl -s -X POST http://127.0.0.1:8104/business/dubbo/buy2 \
  -H 'Content-Type: application/json' \
  -d '{"userId":1,"commodityCode":"C201901140001","name":"fan","count":50,"amount":"100"}'
# 期望：HTTP 500（business 故意抛 RuntimeException，message="测试抛异常后，分布式事务回滚！"）
```

TC 日志应出现：`GlobalRollbackRequest` → 3 条 `BranchRollbackResponse{... PhaseTwo_Rollbacked}` → `Rollback global transaction successfully` → `GlobalRollbackResponse{globalStatus=Rollbacked}`。

### 6.3 数据终态核对（只读）

```sql
-- 期望：库存 = 初始 − 50（buy 生效，buy2 已回滚）
SELECT * FROM seata_demo.t_storage;   -- 初始 1000 → 950
SELECT * FROM seata_demo.t_account;   -- 初始 4000.00 → 3900.00
SELECT * FROM seata_demo.t_order;     -- 仅 buy 产生的那 1 条
SELECT COUNT(*) FROM seata_demo.undo_log;  -- 0（二阶段后清理干净）
```

## 7. 踩坑清单（按本次实测顺序）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 客户端报 `can not connect to [172.18.0.1:8091]` | TC 的 `preferred-networks: 30.240.*` 网段本机不存在，选错网卡注册到 xray 虚拟网卡 172.18.0.1 | TC application.yml 改 `preferred-networks: 192.168.43.*` 后重启 |
| 2 | TC 收到 `GlobalBeginRequest` 后不回包，客户端 `RPC timeout` 30s；TC 日志 `ERROR ... 0104` + `NoSuchMethodError: ByteBuffer.clear()Ljava/nio/ByteBuffer;` at `GlobalSession.encode` | **Seata 2.6.0 server 需要 JDK 9+**，跑 JDK 8 抛 NoSuchMethodError | TC 换 JDK 17 重启（样例服务仍可用 JDK 8） |
| 3 | TC 启动 `NoClassDefFoundError: SpringApplication` | PropertiesLauncher 缺 classpath | 补 `-Dloader.path=<seata-server>/lib` |
| 4 | 尝试 `registry.type=file` + `service.grouplist.default` 直连 TC，yml/-D/-- 三种注入全失败，报 `service.default.grouplist or service.grouplist.default configuration item is required` | Seata 2.6.0 客户端初始化早于 Spring 配置桥接，file registry 的 grouplist 读不到 | 放弃 grouplist 直连，回归 `registry.type=nacos` + camelCase `vgroupMapping`（本方案正解） |
| 5 | business 启动报 `No provider available for OrderDubboService` | 与 order 并行启动的注册竞态 | 等 order 完全就绪后单独重启 business |
| 6 | 沙箱内 `nohup` 长驻进程被回收 | 执行器收割子进程 | 用终端前台或任务托管方式运行长驻服务 |

## 8. 拓扑小结

```
curl → business(8104) @GlobalTransactional
          ├─ Dubbo → storage(8109)   扣库存    ┐
          ├─ Dubbo → order(8101)      建订单     ├─ 每步先写 undo_log
          │           └─ Dubbo → account(8102) 扣余额  ┘
          └─ 正常：GlobalCommit → 3 branch PhaseTwo_Committed → 删除 undo_log
            异常(buy2)：GlobalRollback → 3 branch PhaseTwo_Rollbacked → 按 undo_log 反向补偿

XID 经 Dubbo attachment 在 4 服务间透传；TC(8091) 通过 Nacos 被发现，
vgroup → cluster default → TC 实例 192.168.43.156:8091。
```
