## 3. 前置：Nacos 侧 Seata 配置（SEATA_GROUP）

Seata 2.x 客户端按 `service.vgroupMapping.<事务组>=<集群名>` 找 TC 集群，配置项存在 Nacos `SEATA_GROUP` 中，**必须用 camelCase**（`vgroupMapping`），1.x 的下划线版 `vgroup_mapping` 不生效。

4 个服务各自的事务组 → 全部映射到默认集群 `default`：

```text
service.vgroupMapping.business-service-seata-service-group = default
service.vgroupMapping.order-service-seata-service-group    = default
service.vgroupMapping.account-service-seata-service-group  = default
service.vgroupMapping.storage-service-seata-service-group  = default
```

批量写入用 Seata 发行包自带的脚本（读同目录 `config.txt`，group 默认 `SEATA_GROUP`）：

```bash
cd /Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/script/config-center/nacos
sh nacos-config.sh -h 127.0.0.1 -p 8848 -g SEATA_GROUP
# 参数：[-h host] [-p port] [-g group] [-t tenant] [-u username] [-w password]
```

单条增删查用 Nacos HTTP API（Nacos 2.4.3 仍兼容 v1 接口）：

```bash
# 查
curl -s "http://127.0.0.1:8848/nacos/v1/cs/configs?dataId=service.vgroupMapping.business-service-seata-service-group&group=SEATA_GROUP"
# 发布（content 就是集群名 default）
curl -s -X POST "http://127.0.0.1:8848/nacos/v1/cs/configs" \
  -d "dataId=service.vgroupMapping.business-service-seata-service-group&group=SEATA_GROUP&content=default"
# 删除
curl -s -X DELETE "http://127.0.0.1:8848/nacos/v1/cs/configs?dataId=service.vgroupMapping.business-service-seata-service-group&group=SEATA_GROUP"
```

## 4. 启动 Seata Server（TC）——最容易踩坑的一步

### 4.1 前置：确认 TC 注册 IP 正确（最高频故障点）

TC 启动时会把本机某个网卡 IP 注册到 Nacos，四个样例服务靠这条注册找 TC。**选错网卡 → 四个服务全部起不来**，且报错伪装成"连不上 TC"。

**Seata 选 IP 的规则**（读 `NetUtil.getLocalAddress0` 字节码得出，非推测）：

1. 遍历所有 `isUp` 的网卡，跳过回环地址 —— `127.0.0.1` / `::1` 在扫描阶段就被过滤，**写 `preferred-networks: 127.0.0.1` 是无效的**；
2. 顺手记住**第一个合法地址**，作为兜底；
3. 若配了 `preferred-networks`，对每个地址做 `matches()` / `startsWith()` 匹配，**命中立即返回**；
4. 若全都不匹配 → 打 ERROR `Could not match ip by preferredNetworks:{} , will use default first ip {} instead.`，然后**回退到第 2 步的"第一个合法地址"**。

第 4 条是坑的核心。而 macOS 上 Java 枚举网卡是**按下标倒序**的（后建的网卡排在前面），实测顺序：

```text
#1 utun3(21)  #2 utun2(20)  #3 utun1(19)  #4 utun0(18)  #5 llw0(17)  #6 awdl0(16)
#7 en0(14) → 192.168.5.3   ← 唯一真正可用的地址
#8 lo0(1)  → 127.0.0.1     ← 被过滤
```

所以**代理软件的 `utun4`（index=22）永远排在 `en0` 前面**：`preferred-networks` 一旦匹配不上，兜底就选中 TUN 网卡的 `198.18.0.1`。

**修法**：把网段放宽到能覆盖当前 LAN 的模式（本文档已按此修正并实测通过）：

```yaml
registry:
  type: nacos
  preferred-networks: 192.168.*   # ← 原为 192.168.43.*，换网络后失效
  nacos:
    server-addr: 127.0.0.1:8848
    group: SEATA_GROUP
    cluster: default
```

写成 `192.168.*` 后，即使 `utun4` 排在最前也不会命中，扫描会继续到 `en0` 命中并立即返回 —— **顺序敏感问题被消除，VPN 开着也能正常注册**。

改前备份：`cp conf/application.yml conf/application.yml.bak`。改完**必须重启 TC**，因为 IP 只在注册那一刻算一次。

> **⚠️ 关 VPN 解决不了这个问题。** Nacos 里那条例册是 TC 注册的临时实例，靠 TC 自己的心跳续命，Nacos 从不校验 IP 是否真实存在。两种表现：
>
> | VPN | 现象 | 客户端日志特征 |
> |---|---|---|
> | 开着 | `utun4` 存在，TC 注册 `198.18.0.1:8091`。TCP 能握手（TUN 接单）但数据被吞 | `register TMROLE error, errMsg:null ,cost: 30012 ms`（30s 超时），随后 `can not connect to [198.18.0.1:8091]` |
> | 关掉 | `utun4` 消失，**但 Nacos 里 `198.18.0.1` 那条还在**（TC 没重启就不会重注册） | `connect failed, can not connect to services-server`（10s，`NettyClientBootstrap.getNewChannel`） |
>
> 两种情况都必须**改配置 + 重启 TC**。

> **客户端侧不用改。** 实测给样例服务加 `-Dseata.registry.preferred-networks=10.99.*` 后，客户端既不打印 `Could not match ip` 警告、自报 IP 仍是 `192.168.5.3`，说明**客户端不读这个配置项**，它只走上面的"第一个合法地址"逻辑。客户端自报 IP 仅用于日志，不影响连 TC。

### 4.2 启动命令（两个硬性要求）

- **JDK 必须 9+（实测 17）**：Seata 2.6.0 server 字节码引用了 JDK 9+ 的 `ByteBuffer.clear()` 协变返回 API，用 JDK 8 跑会在 `GlobalSession.encode` 抛 `NoSuchMethodError`，TC 吞异常不回包，客户端表现为 `GlobalBeginRequest ... RPC timeout` 30s。
- **必须 `-Dloader.path`**：seata-server.jar 是 Spring Boot PropertiesLauncher，不带该参数会 `NoClassDefFoundError: org/springframework/boot/SpringApplication`。

```bash
cd /Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server

/Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home/bin/java \
  -Dlog.home=/Users/yangchao/logs/seata \
  -Dloader.path=/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/lib \
  -Dspring.config.additional-location=/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/conf/ \
  -Dspring.config.location=/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/conf/application.yml \
  -jar target/seata-server.jar
```

启动成功标志（日志）：

```text
Server started, service listen port: 8091
```

并在 Nacos 服务列表出现本机真实 IP 的实例（healthy=true），服务名 `seata-server`，例如 `192.168.5.3:8091`。
用下面的命令直接确认注册 IP，**这里看到的必须是本机 `ipconfig getifaddr en0` 的值**：

```bash
curl -s "http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=seata-server&groupName=SEATA_GROUP"
# 若返回的 ip 是 198.18.0.1 / 172.18.0.1 之类的虚拟网卡地址，说明 preferred-networks 没匹配上，回到 4.1 改
```

> 注意：在受管环境（AI 执行器、CI）里用 `nohup ... &` 起长驻进程会**被连带回收**（表现为进程起来了、日志也正常，
> 但命令一结束就消失）。要让 TC 真正常驻，需让它脱离当前进程组，例如：
>
> ```python
> subprocess.Popen(cmd, cwd=BASE, stdout=open(log, "w"),
>                  stdin=subprocess.DEVNULL, start_new_session=True)   # ← 关键
> ```
>
> 最省事的还是**在自己终端里直接跑** `sh bin/seata-server.sh`。
> 本文档 00:32 那次的验证就是这么起的：TC PID 39650 存活、注册 `192.168.5.3:8091`。

## 5. 启动 4 个样例服务（顺序是硬性的）

### 5.1 谁依赖谁

启动顺序由 Dubbo 引用方向决定，`@DubboReference` 注在**消费方**：

```
business ──@DubboReference──→ storage       扣库存
        └──@DubboReference──→ order ──@DubboReference──→ account   扣余额
```

| 依赖关系 | 代码位置 |
|---|---|
| business → storage、order | `BusinessServiceImpl` 两个 `@DubboReference` 字段 |
| order → account | `TOrderServiceImpl` 的 `accountDubboService` 字段 |
| account、storage | 纯提供者，没有下游 |

### 5.2 正确顺序

1. **account、storage** —— 两者互不依赖，可同时起，顺序任意
2. **order** —— 它要调 account
3. **business** —— 它要调 order 和 storage

### 5.3 为什么是硬性的（不是"建议"）

代码里写的是 `@DubboReference(version = "1.0.0")`，**没有 `check = false`**，
而 dubbo 2.7.13 的 `@DubboReference#check` 注解默认值是 **`true`**。
`check=true` 的含义是：消费端在启动（refer）阶段就要校验提供者是否已注册，不存在直接抛异常：

```text
IllegalStateException: Failed to check the status of the service
io.seata.samples.integration.common.dubbo.AccountDubboService.
No provider available for the service
io.seata.samples.integration.common.dubbo.AccountDubboService:1.0.0 ...
```

这个异常抛在 `ReferenceBean.getObject()`，也就是 Spring 容器 refresh 阶段，
**后果是应用直接启动失败退出**，而不是"起来了、调用时才报错"。
所以先起 order 再起 account，order 必定启动失败——这是必然结果，不是偶发的注册竞态。

> 实测方式（不启 Spring、不连 MySQL，直接用本工程 fat jar 里的 dubbo 依赖跑一个裸 `ReferenceConfig` 指向 Nacos 8848）：
> `check=true` + 无提供者 → 1253ms 抛上述 `IllegalStateException`；
> `check=false` → 1164ms 正常拿到代理。两种行为均已复现。

### 5.4 想让顺序不敏感（可选，当前未改）

- 逐处改：business 的 2 个 + order 的 1 个 `@DubboReference` 加 `check = false`
- 或全局改：business / order 的 `application.yml` 加

```yaml
dubbo:
  consumer:
    check: false
```

注意 `check=false` 只是跳过**启动期**校验，提供者仍缺失时调用照样失败，
只是把错误从启动期推迟到调用期。调试阶段图省事可以这么干，正式跑建议仍按顺序启动。

> 顺带：business / order 的 yml 里有 `dubbo.consumer.provided-by: ...`，
> 但 dubbo 2.7.13 并没有 `providedBy` 这个属性（是 3.x 才加的），属于被静默忽略的死配置，
> 不要误以为它能替代启动顺序。

## 6. 验证分布式事务

### 6.1 正常提交 buy

```bash
curl -s -X POST http://127.0.0.1:8104/business/dubbo/buy \
  -H 'Content-Type: application/json' \
  -d '{"userId":1,"commodityCode":"C201901140001","name":"fan","count":50,"amount":"100"}'
# 期望：{"status":200,"message":"成功","data":null}（约 1~2s 返回）
```

TC 日志应出现：`GlobalBeginResponse{resultCode=Success}` → 3 条 `BranchCommitResponse{... PhaseTwo_Committed}`（storage/account/order 各一）→ `Committing global transaction is successfully done`。

### 6.2 异常回滚 buy2

```bash
curl -s -X POST http://127.0.0.1:8104/business/dubbo/buy2 \
  -H 'Content-Type: application/json' \
  -d '{"userId":1,"commodityCode":"C201901140001","name":"fan","count":50,"amount":"100"}'
# 期望：HTTP 500（business 故意抛 RuntimeException，message="测试抛异常后，分布式事务回滚！"）
```

TC 日志应出现：`GlobalRollbackRequest` → 3 条 `BranchRollbackResponse{... PhaseTwo_Rollbacked}` → `Rollback global transaction successfully` → `GlobalRollbackResponse{globalStatus=Rollbacked}`。

## 7. 踩坑清单（按本次实测顺序）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 客户端报 `can not connect to [198.18.0.1:8091]`，account / storage 全部启动失败 | TC 的 `preferred-networks` 匹配不上本机网卡 → 回退选"第一个合法地址"，而 macOS 上 Java 按**下标倒序**枚举网卡，代理的 `utun4`(198.18.0.1) 排在 `en0`(192.168.5.3) 前面。历史配置 `192.168.43.*` 在 9/3、9/4 时是对的（当时 xid 前缀 `192.168.43.156:8091`），本机换成 192.168.5.x 后失效 | 见 4.1：改成 `preferred-networks: 192.168.*` 并**重启 TC**。实测重启后注册变为 `192.168.5.3:8091`，account 服务 `register TM success 89ms` / `register RM success 7ms`，启动成功 |
| 2 | TC 收到 `GlobalBeginRequest` 后不回包，客户端 `RPC timeout` 30s；TC 日志 `ERROR ... 0104` + `NoSuchMethodError: ByteBuffer.clear()Ljava/nio/ByteBuffer;` at `GlobalSession.encode` | **Seata 2.6.0 server 需要 JDK 9+**，跑 JDK 8 抛 NoSuchMethodError | TC 换 JDK 17 重启（样例服务仍可用 JDK 8） |
| 3 | TC 启动 `NoClassDefFoundError: SpringApplication` | PropertiesLauncher 缺 classpath | 补 `-Dloader.path=<seata-server>/lib` |
| 4 | 尝试 `registry.type=file` + `service.grouplist.default` 直连 TC，yml/-D/-- 三种注入全失败，报 `service.default.grouplist or service.grouplist.default configuration item is required` | Seata 2.6.0 客户端初始化早于 Spring 配置桥接，file registry 的 grouplist 读不到 | 放弃 grouplist 直连，回归 `registry.type=nacos` + camelCase `vgroupMapping`（本方案正解） |
| 5 | business 启动报 `No provider available for OrderDubboService` | `@DubboReference` 未设 `check=false`，而注解默认 `check=true`：refer 阶段就校验提供者，缺失即抛 `IllegalStateException` 致启动失败。**这是必然结果，不是偶发竞态**——只要 order / storage 没先起来，business 一定起不来 | 按 5.2 的顺序启动（account/storage → order → business）；或按 5.4 给 `@DubboReference` 加 `check=false` |
| 6 | 沙箱内 `nohup` 长驻进程被回收 | 执行器收割子进程 | 用终端前台或任务托管方式运行长驻服务 |

## 8. 拓扑小结

```
curl → business(8104) @GlobalTransactional
          ├─ Dubbo → storage(8109)   扣库存    ┐
          ├─ Dubbo → order(8101)      建订单     ├─ 每步先写 undo_log
          │           └─ Dubbo → account(8102) 扣余额  ┘
          └─ 正常：GlobalCommit → 3 branch PhaseTwo_Committed → 删除 undo_log
            异常(buy2)：GlobalRollback → 3 branch PhaseTwo_Rollbacked → 按 undo_log 反向补偿

XID 经 Dubbo attachment 在 4 服务间透传；TC(8091) 通过 Nacos 被发现，
vgroup → cluster default → TC 实例 192.168.5.3:8091（随本机网卡 IP 变化，详见 4.1）。
```
