## 3. 前置：Nacos 侧 Seata 配置（SEATA_GROUP）

Seata 2.x 客户端按 `service.vgroupMapping.<事务组>=<集群名>` 找 TC 集群，配置项存在 Nacos `SEATA_GROUP` 中，**必须用 camelCase**（`vgroupMapping`），1.x 的下划线版 `vgroup_mapping` 不生效。

4 个服务各自的事务组 → 全部映射到默认集群 `default`：

```text
service.vgroupMapping.business-service-seata-service-group = default
service.vgroupMapping.order-service-seata-service-group    = default
service.vgroupMapping.account-service-seata-service-group  = default
service.vgroupMapping.storage-service-seata-service-group  = default
```

批量写入用 Seata 发行包自带的脚本（读同目录 `config.txt`，group 默认 `SEATA_GROUP`）：

```bash
cd /Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/script/config-center/nacos
sh nacos-config.sh -h 127.0.0.1 -p 8848 -g SEATA_GROUP
# 参数：[-h host] [-p port] [-g group] [-t tenant] [-u username] [-w password]
```

单条增删查用 Nacos HTTP API（Nacos 2.4.3 仍兼容 v1 接口）：

```bash
# 查
curl -s "http://127.0.0.1:8848/nacos/v1/cs/configs?dataId=service.vgroupMapping.business-service-seata-service-group&group=SEATA_GROUP"
# 发布（content 就是集群名 default）
curl -s -X POST "http://127.0.0.1:8848/nacos/v1/cs/configs" \
  -d "dataId=service.vgroupMapping.business-service-seata-service-group&group=SEATA_GROUP&content=default"
# 删除
curl -s -X DELETE "http://127.0.0.1:8848/nacos/v1/cs/configs?dataId=service.vgroupMapping.business-service-seata-service-group&group=SEATA_GROUP"
```

## 4. 启动 Seata Server（TC）——最容易踩坑的一步

> **⚠️ 每次开机 / 换 Wi-Fi / 换网段后，先做这一步自检。**
> 本机 IP 会变，但 Nacos 里的注册 IP 是 **TC（及各服务）启动那一刻**算出来写进去的，**不会自动更新**。
> 只要两者不一致，所有客户端都会去连一个已经不存在的地址，表现为"TC 明明在跑，服务却连不上"。
>
> ```bash
> # 一行核对：本机 IP  vs  Nacos 里 seata-server 的注册 IP
> echo "local = $(ipconfig getifaddr en0)"
> curl -s "http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=seata-server&groupName=SEATA_GROUP" \
>   | tr ',' '\n' | grep '"ip"'
> ```
>
> 不一致（例：local=`192.168.43.156`，Nacos=`192.168.5.3`）→ **重启 TC**；
> 同理，**已经跑着的 4 个样例服务也要重启**（它们注册到 Nacos 的 Dubbo IP 同样是旧值）。
> 详见 `问题记录.md` #001 / #003。

### 4.1 前置：确认 TC 注册 IP 正确（最高频故障点）

TC 启动时会把本机某个网卡 IP 注册到 Nacos，四个样例服务靠这条注册找 TC。**选错网卡 → 四个服务全部起不来**，且报错伪装成"连不上 TC"。

> **⚠️ 先破除一个常见误解：「yml 里写的全是 127.0.0.1，为什么还会受 IP 变化影响？」**
>
> 一行配置里其实是**两个语义完全不同的 IP**：
>
> | | 含义 | 谁在用 | 本项目实测值 |
> | --- | --- | --- | --- |
> | `nacos://127.0.0.1:8848`（写在 yml 里） | **去哪注册** —— Nacos 服务端地址 | 各服务**主动连出去** | `127.0.0.1`（写死的，永不变化） |
> | Nacos 里那条实例记录的 IP | **注册成什么** —— 自报家门地址 | 别人**拿它来连你** | `192.168.43.156`（探测网卡得来，**会变**） |
>
> 关键点：**消费者不是拿自己 yml 里的 `127.0.0.1` 去连提供者，而是从 Nacos 取回提供者"自报的地址"再去连。**
> 所以哪怕 4 个服务全在同一台机器上，实际 RPC 走的也是**真实网卡 IP**，不是 `lo0`。
> 而框架**在网卡扫描阶段就剔除回环地址**（见下）—— 你既无法、也不应指望"注册成 127.0.0.1"。
> 结论：换网络 → 自报地址必然改变 → 注册表里的旧地址成为死地址 → **只能重启**（TC + 所有已运行服务）。
>
> **那能不能干脆全部强制成 `127.0.0.1`，一劳永逸？——不建议，因为改不齐。**
> Dubbo 侧可以（`dubbo.protocol.host` 是 `ProtocolConfig` 的真实字段，或设环境变量），
> 但 **Seata 侧做不到**：反编译 `seata-all-2.6.0` 的 `NetUtil`，全类搜不到任何 `register-ip` / `host` 直配项，
> 只有 `preferred-networks`，而回环在"匹配之前"就被剔除（`isValidAddress` 首行即 `isLoopbackAddress()` → return false），
> `preferred-networks: 127.*` 永远匹配不上，只会回退到"第一个合法地址"。
> 两边改不齐 → 环境照样被 IP 漂移打断，所以本项目选择**不强制、换网后重启**这条更省事的路。
>
> **重启范围速查**（实测依据见 `问题记录.md` #003 六）：
>
> | 场景 | TC | 4 个业务服务 |
> | --- | --- | --- |
> | 开关 VPN，LAN 网段未变 | ❌ 通常不用（TUN 是 198.18.x，匹配不上 `192.168.*` 会被跳过） | ❌ 不用 |
> | 换 Wi-Fi / 换网段（本机 IP 变） | ✅ **必须重启** | ✅ **要重启** —— 为修它们自己的 Dubbo 注册 |
> | 仅 TC 单方面重启（本机 IP 未变） | —— | ❌ **不用**，10s 内自动跟随（客户端重连时会重新 `lookup()` 注册表） |

**Seata 选 IP 的规则**（读 `NetUtil.getLocalAddress0` 字节码得出，非推测）：

1. 遍历所有 `isUp` 的网卡，跳过回环地址 —— `127.0.0.1` / `::1` 在扫描阶段就被过滤，**写 `preferred-networks: 127.0.0.1` 是无效的**；
2. 顺手记住**第一个合法地址**，作为兜底；
3. 若配了 `preferred-networks`，对每个地址做 `matches()` / `startsWith()` 匹配，**命中立即返回**；
4. 若全都不匹配 → 打 ERROR `Could not match ip by preferredNetworks:{} , will use default first ip {} instead.`，然后**回退到第 2 步的"第一个合法地址"**。

第 4 条是坑的核心。而 macOS 上 Java 枚举网卡是**按下标倒序**的（后建的网卡排在前面），实测顺序：

```text
#1 utun3(21)  #2 utun2(20)  #3 utun1(19)  #4 utun0(18)  #5 llw0(17)  #6 awdl0(16)
#7 en0(14) → 本机 IP       ← 唯一真正可用的地址（当时是 192.168.5.3，随网络变化）
#8 lo0(1)  → 127.0.0.1     ← 被过滤
```

所以**代理软件的 `utun4`（index=22）永远排在 `en0` 前面**：`preferred-networks` 一旦匹配不上，兜底就选中 TUN 网卡的 `198.18.0.1`。

**修法**：把网段放宽到能覆盖当前 LAN 的模式（本文档已按此修正并实测通过）：

```yaml
registry:
  type: nacos
  preferred-networks: 192.168.*   # ← 原为 192.168.43.*，换网络后失效
  nacos:
    server-addr: 127.0.0.1:8848
    group: SEATA_GROUP
    cluster: default
```

写成 `192.168.*` 后，即使 `utun4` 排在最前也不会命中，扫描会继续到 `en0` 命中并立即返回 —— **顺序敏感问题被消除，VPN 开着也能正常注册**。

改前备份：`cp conf/application.yml conf/application.yml.bak`。改完**必须重启 TC**，因为 IP 只在注册那一刻算一次。

> **⚠️ 关 VPN 解决不了这个问题。** Nacos 里那条例册是 TC 注册的临时实例，靠 TC 自己的心跳续命，Nacos 从不校验 IP 是否真实存在。两种表现：
>
> | VPN | 现象                                                       | 客户端日志特征                                                                                                |
> | --- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
> | 开着  | `utun4` 存在，TC 注册 `198.18.0.1:8091`。TCP 能握手（TUN 接单）但数据被吞  | `register TMROLE error, errMsg:null ,cost: 30012 ms`（30s 超时），随后 `can not connect to [198.18.0.1:8091]` |
> | 关掉  | `utun4` 消失，**但 Nacos 里 `198.18.0.1` 那条还在**（TC 没重启就不会重注册） | `connect failed, can not connect to services-server`（10s，`NettyClientBootstrap.getNewChannel`）         |
>
> 两种情况都必须**改配置 + 重启 TC**。

> **客户端侧不用改。** 实测给样例服务加 `-Dseata.registry.preferred-networks=10.99.*` 后，客户端既不打印 `Could not match ip` 警告、自报 IP 仍是 `192.168.5.3`，说明**客户端不读这个配置项**，它只走上面的"第一个合法地址"逻辑。客户端自报 IP 仅用于日志，不影响连 TC。

## 5. 启动 4 个样例服务（顺序是硬性的，Dubbo 3 下依然如此）

### 5.1 谁依赖谁

启动顺序由 Dubbo 引用方向决定，`@DubboReference` 注在**消费方**：

```
business ──@DubboReference──→ storage       扣库存
        └──@DubboReference──→ order ──@DubboReference──→ account   扣余额
```

| 依赖关系                     | 代码位置                                           |
| ------------------------ | ---------------------------------------------- |
| business → storage、order | `BusinessServiceImpl` 两个 `@DubboReference` 字段  |
| order → account          | `TOrderServiceImpl` 的 `accountDubboService` 字段 |
| account、storage          | 纯提供者，没有下游                                      |

### 5.2 正确顺序

1. **account、storage** —— 两者互不依赖，可同时起，顺序任意
2. **order** —— 它要调 account
3. **business** —— 它要调 order 和 storage


### 5.3 为什么是硬性的（不是"建议"）

代码里写的是 `@DubboReference(version = "1.0.0")`，**没有 `check = false`**，  
而 `@DubboReference#check` 注解默认值是 **`true`**（Dubbo 2.7.13 与 3.3.6 一致）。  
`check=true` 的含义是：消费端在启动阶段要校验提供者是否已注册，不存在就抛异常、**应用启动失败**：

```text
java.lang.IllegalStateException: Failed to check the status of the service
io.seata.samples.integration.common.dubbo.AccountDubboService. No provider available for the service
io.seata.samples.integration.common.dubbo.AccountDubboService:1.0.0 ...
```

所以先起 order 再起 account，order 必定启动失败——这是必然结果，不是偶发的注册竞态。  
**结论在 Dubbo 3 下依然成立**，但失败时机和日志形态变了，见下。

**⚠️ Dubbo 3 的行为差异（重要）：失败被推迟约 30 秒，且中途会打印"看起来已启动"的日志。**

升级到 3.3.6 后实测（停掉 account，单独起一个 order 实例复现）：

```text
01:51:01.233  TomcatWebServer            : Tomcat initialized with port(s): 18101 (http)      ← Tomcat 已起来
01:51:03.864  MigrationRuleHandler       : Succeed Migrated to APPLICATION_FIRST mode.
01:51:03.864  ReferenceConfig            : Referred dubbo service: [AccountDubboService].      ← 代理也创建成功了
01:51:03.866  DefaultApplicationDeployer : Dubbo Application[dubbo-order-example] is ready.   ← 陷阱：这不是"应用已启动"
        ……（此处静默轮询 30 秒）……
01:51:33.918  WARN  ReferenceConfig      : Check reference of [AccountDubboService:1.0.0] failed
                                           very beginning. After 30003ms reties, finally failed.
01:51:33.944  ERROR DefaultModuleDeployer: Model start failed: ... Failed to check the status of the service …
（注意：全程【没有】打印 "Started OrderExampleApplication"）
```

即：日志先出现 `Referred dubbo service` / `Migrated to APPLICATION_FIRST mode` / `Dubbo Application is ready`，  
**约 30 秒后**才抛 `IllegalStateException`、让 Spring Boot 启动失败。  
**别被中间那几行 INFO 骗了**——它们只代表 Dubbo 模块就绪，不代表 Spring 启动完成。

机制（反编译 `dubbo-3.3.6.jar` 得到，非推测）：

```text
DubboDeployApplicationListener.onContextRefreshedEvent   ← 注意：在 Spring 上下文 refresh 完成【之后】才触发
  └─ DefaultModuleDeployer.startSync
       └─ DefaultModuleDeployer.checkReferences()        ← 超时值 = ModuleConfig.checkReferenceTimeout
            └─ SimpleReferenceCache.check(ref, timeout)   ← 默认 30000ms（字节码 ldc2_w 30000l）
                 └─ ReferenceConfig.checkOrDestroy(timeout)
                      └─ ReferenceConfig.checkInvokerAvailable(timeout)
                           └─ while (!invoker.isAvailable() && now < deadline) Thread.sleep(100)  ← 每 100ms 轮询一次
                                ↓ 到点仍未就绪
                                throw IllegalStateException("Failed to check the status of the service …")
```

- 超时**可覆盖**：配置项 `dubbo.module.check-reference-timeout`（单位毫秒，默认 `30000`）。  
  想让它"立即失败"就设成 `0`（此时只轮询一次、约 100ms 内抛错）。
- 因为校验挂在 `onContextRefreshedEvent` 上（位于 `refresh()` 末尾的 `finishRefresh()`，**早于** Spring Boot 打印 `Started ...Application`），  
  此时 Tomcat 已监听端口、所有 Bean 都建完了，只差最后一段校验——所以日志极容易被误读为"启动成功了"。  
  实测这一次**全程没有**打印 `Started OrderExampleApplication`。

> 对比：升级前（Dubbo 2.7.13）同一场景是**秒级快速失败**（实测裸 `ReferenceConfig` 约 1253ms 抛异常），  
> 且失败点更靠前。这个"30 秒静默等待 + 中途打印 ready"是 Dubbo 3 才有的新形态。

### 5.4 想让顺序不敏感（可选，当前未改）

- 逐处改：business 的 2 个 + order 的 1 个 `@DubboReference` 加 `check = false`
- 或全局改：business / order 的 `application.yml` 加

```yaml
dubbo:
  consumer:
    check: false
```

注意 `check=false` 只是跳过**启动期**校验，提供者仍缺失时调用照样失败，  
只是把错误从启动期推迟到调用期。调试阶段图省事可以这么干，正式跑建议仍按顺序启动。

> 顺带：business / order 的 yml 里原来各有一段 `dubbo.consumer.provided-by: ...`，升级 Dubbo 3 时已删除。  
> 它在 Dubbo 2.7.13 下本就是死配置（`ConsumerConfig` 无 `providedBy` 属性，静默忽略）；  
> Dubbo 3.x 虽引入了 `providedBy`，但其语义是"消费端持续等待指定提供者应用上线"，与"启动顺序"不是一回事，  
> **不要误以为它能替代 §5.2 的启动顺序**。

> 动机：真实项目统一使用 Dubbo 3.x，本学习工程同步升级以对齐。  
> 升级后已重新端到端复测：4 服务启动、`buy` 提交、`buy2` 回滚、XID 穿透、tag 隔离全部通过。

### 9.1 版本矩阵

| 组件                          | 升级前                     | 升级后               | 说明                                                                                          |
| --------------------------- | ----------------------- | ----------------- | ------------------------------------------------------------------------------------------- |
| Dubbo                       | 2.7.13                  | **3.3.6**         | 3.x 分支                                                                                      |
| netty                       | 4.1.42.Final（胖包）        | **4.1.101.Final** | 取 Dubbo 3.3.6（声明 4.2.2）与 Seata 2.6.0（声明 4.1.101）的安全交集                                       |
| dubbo-filter-seata          | 1.0.2（`seata-all` 传递引入） | **3.3.1**（显式覆盖）   | 1.0.2 引用 `io.seata.*` 老包名（走 Seata 2.x 兼容层）；3.3.1 引用 `org.apache.seata.*`，与 Seata 2.6.0 原生对齐 |

### 9.2 依赖收敛（根 `pom.xml`）

- `dubbo-spring-boot-starter` → `dubbo-spring-boot-autoconfigure` → `dubbo`（**all-in-one 聚合包**，已内含 `dubbo-config-spring` / `dubbo-cluster` / `dubbo-configcenter-nacos` / `dubbo-metadata-report-nacos`）。因此原来单独声明的 `dubbo`、`dubbo-config-spring` 属重复声明，**已移除**。
- 新增 `org.apache.dubbo:dubbo-registry-nacos:3.3.6` 与 `org.apache.dubbo.extensions:dubbo-filter-seata:3.3.1`。
- 移除 `com.alibaba.spring:spring-context-support:1.0.11`（Dubbo 2.7 的 `@EnableDubbo` 配置绑定遗留依赖，Dubbo 3 已自带同等能力）。
- `netty-all` 去掉老版本钉死，统一由 `<netty.version>4.1.101.Final</netty.version>` 控制。
  > 关键认知：`netty-all` 自 **4.1.91** 起已改为"空壳聚合器"（0 个类，只声明各 `netty-*` 子模块依赖）；  
  > 而 4.1.42 那种是含 2667 个类的"胖包"，会与子模块产生**重复类**。所以这个版本**不能往 4.1.91 以下回退**。  
  > 已核实 Dubbo 3.3.6 未使用任何 netty 4.2 独有 API（`IoHandler` / `MultiThreadIoEventLoopGroup` 等），故锁定 4.1.101 对 Dubbo 侧也安全。

### 9.4 ⚠️ 最容易踩的坑：`dubbo.force.tag` 必须写"点号"形式

想让 tag 严格隔离（找不到同 tag 的提供者时直接失败、不回退），需给消费端加 `dubbo.force.tag=true`。  
但 **Spring 惯用的方括号写法在 Dubbo 3 里绑不进去**：

```yaml
# ❌ 不生效：force.tag 不会出现在消费端 URL 上，隔离形同虚设
dubbo:
  consumer:
    parameters:
      "[dubbo.force.tag]": "true"
```

```yaml
# ✅ 生效：实测消费端 URL 出现 dubbo.force.tag=true
dubbo:
  consumer:
    parameters:
      dubbo.force.tag: "true"
```

根因：`parameters` 字段定义在 `AbstractMethodConfig` 上，Dubbo 自己的绑定器**不展开** `[xxx]` 这种方括号 key  
（方括号是 Spring Boot 对 `Map` 属性的宽松绑定语法，但 Dubbo 的属性绑定不走 Spring 那一套）。

**验证方法**：消费端启动后，在日志里 grep 消费端 URL 是否含 `dubbo.force.tag=true`（就是 `consumer://...` 那一行）。  
若只有 `dubbo.tag=dev` 而没有 `dubbo.force.tag=true`，即说明没绑上。

> 附带：Dubbo 3 的标签路由实现由 2.7 的 `TagRouter` / `TagRouterFactory` 更名为 **`TagStateRouter` / `TagStateRouterFactory`**  
> （仍是 `@Activate(order = 100)`、默认启用）。名字变了，行为语义不变——本文档的 tag 隔离方案在 3.3.6 上原样可用。

### 9.5 tag 隔离复测结论（Dubbo 3.3.6）

| 验证项                                | 结果                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------- |
| 同 tag（`dev`）互联                     | 正常调用；11 次 `buy2` 全部命中 `dev` 的 storage 实例                                          |
| 异 tag 实例（`other`）                  | **0 次调用**（被 `TagStateRouter` 过滤掉）                                                 |
| 消费端 `tag=other` + `force.tag=true` | 调用时抛 `No provider available for StorageDubboService`（invokers 存在但被过滤，force 阻止了回退） |

### 9.6 复现"provider 缺失导致启动失败"的命令

```bash
# 1) 停掉 account（或任一下游提供者）
# 2) 单独起一个 order（换端口，避免与已在跑的实例冲突）
java -jar samples-order/target/samples-order-1.0.0.jar \
     --server.port=18101 --dubbo.protocol.port=20980
# 3) 观察日志：先出现 Application is ready，约 30s 后：
#    WARN  ReferenceConfig       : Check reference of [AccountDubboService:1.0.0] failed very beginning.
#                                  After 30003ms reties, finally failed.
#    ERROR DefaultModuleDeployer : Model start failed: ... Failed to check the status of the service …
```
