## 问题 #001：TC 注册到虚拟网卡 `198.18.0.1`，导致 account / storage 启动失败

### 基本信息

| 项 | 内容 |
|---|---|
| 发现时间 | 2026-09-11 00:16 |
| 状态 | ✅ 已修复并端到端验证 |
| 影响范围 | samples-account、samples-storage（**启动即退出**，非运行期报错）；order / business 未测但同理 |
| 涉及组件 | seata-server 2.6.0（TC，JDK 17.0.12）、seata-all 2.6.0（客户端）、Nacos 2.4.3 |
| 故障类型 | 配置失效 + 网卡选择兜底逻辑，叠加代理软件 fake-ip |
| 修复文件 | `seata-2.6.0/seata-server/conf/application.yml`（第 91 行） |

### 一、现象

account 服务启动时，`globalTransactionScanner` Bean 初始化失败，Spring 容器 refresh 中断，**应用直接退出（exit code 1）**：

```
BeanCreationException: Error creating bean with name 'globalTransactionScanner'
  defined in class path resource [org/apache/seata/spring/boot/autoconfigure/SeataAutoConfiguration.class]:
  Invocation of init method failed;
  nested exception is org.apache.seata.common.exception.FrameworkException:
  can not connect to [198.18.0.1:8091]
    at ...NettyClientChannelManager.doReconnect(NettyClientChannelManager.java:271)
    at ...TmNettyRemotingClient.initConnection(TmNettyRemotingClient.java:333)
    at ...GlobalTransactionScanner.afterPropertiesSet(GlobalTransactionScanner.java:536)
```

目标是 **`198.18.0.1:8091`** —— 本机根本没有这个地址（`en0` 是 `192.168.5.3`）。

**关键对照：VPN 开 / 关，报错形态不同，但都失败。**

| 条件 | 日志关键行 | 耗时 | 底层含义 |
|---|---|---|---|
| VPN 开 | `0101 can not connect to [198.18.0.1:8091] cause:[can not register RM, err:register TMROLE error, errMsg:null, cost: 30012 ms]` | 30 s | TCP 能握手（`nc -vz` 成功），但数据包被 TUN 吞掉，**协议层超时** |
| VPN 关 | `0304 register RM failed` → `connect failed, can not connect to services-server` | 10 s | `198.18.0.1` 彻底不可达，**连接直接失败** |

> 这两种形态一度让人误判为"网络问题"，实际都不是。

### 二、根因

完整因果链（结论均来自读字节码 + 实测，非推测）：

**1. 配置里的网段已失效**

`seata-server/conf/application.yml` 写着：

```yaml
preferred-networks: 192.168.43.*
```

而本机 `en0` 现在是 **`192.168.5.3`**，`192.168.43.*` 匹配不上任何网卡。

历史日志佐证：9/3、9/4 事务正常运行时，xid 前缀是 `192.168.43.156:8091` —— 说明**这条配置当初是对的，是本机换了网段之后才失效**。

**2. Seata 的网卡选择有"兜底回退"**

`NetUtil.getLocalAddress0` 的实际逻辑（反编译 `seata-all-2.6.0.jar` 得到）：

1. 遍历网卡，跳过回环地址（`isValidAddress` 过滤，含 `FORBIDDEN_HOSTS` + `isLoopbackAddress`）
2. **先记下"遇到的第一个合法地址"当兜底**
3. 若配了 `preferred-networks`，逐个匹配，命中即返回
4. **全不匹配时**，打印 `Could not match ip by preferredNetworks:{} , will use default first ip {} instead.`，然后**回退用第 2 步的兜底地址**

第 4 步是要害：配置不匹配**不会报错，而是静默回退**。

**3. macOS 上 Java 枚举网卡是"按下标倒序"的，兜底必然选中虚拟网卡**

纯 JDK 实测枚举顺序（`NetworkInterface.getNetworkInterfaces()` 打印 `getIndex()`）：

```
utun3(21) → utun2(20) → utun1(19) → utun0(18) → llw0(17) → awdl0(16) → en0(14) → lo0(1)
```

代理软件的 TUN 口 `utun4` 的 `index=22`，**排在 `en0`（index=14）之前**。所以第 4 步的兜底地址必然选中 `198.18.0.1`。

> `198.18.0.0/15` 正是 Clash 系列的 **fake-ip** 保留段。

**结论一句话**：配置网段写错 → 静默回退到"第一个合法地址" → macOS 倒序枚举使 TUN 口排在最前 → TC 把 `198.18.0.1:8091` 注册进了 Nacos。

### 三、为什么"关掉 VPN"没有用

因为**坏 IP 是 TC 启动时算出来写进 Nacos 的，与当前网络状态无关**：

- Nacos 里那条 `seata-server` 注册是**临时实例**，靠 **TC 自身心跳**续命。Nacos **从不校验**这个 IP 是否真实存在。
- 关掉 VPN 只是让 `utun4` 消失，**Nacos 里那条 `198.18.0.1:8091` 注册依然在**（TC 未重启就不会重新注册）。
- 于是客户端行为只是从"连上了但超时"变成"连不上直接失败"，**问题依旧**。

必须**重启 TC** 才会重新走一遍网卡选择、覆写注册 IP。

### 四、修复

改动就一行：

```yaml
# seata-server/conf/application.yml 第 91 行
- preferred-networks: 192.168.43.*
+ preferred-networks: 192.168.*
```

```bash
cp -n conf/application.yml conf/application.yml.bak-$(date +%Y%m%d-%H%M%S)   # 备份
kill <旧TC_PID>                                                              # 停旧 TC
export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home  # JDK 8 亦可
sh bin/seata-server.sh                                                       # 重启
```

本次操作留痕：备份 `conf/application.yml.bak-20260911-002910`；旧 TC `PID 20289` → 新 TC `PID 39650`。

**为什么写 `192.168.*` 而不是精确的 `192.168.5.*`：**

通配前缀放宽后，即使 `utun4` 排在最前也不匹配，扫描会继续向下直到 `en0` 命中并返回 —— **网卡枚举顺序的敏感性被消除**。以后换 Wi-Fi（只要仍在 `192.168.x.x` 段）**无需再改配置**，VPN 开着也能正常注册。

### 五、验证（实测链路）

| 环节 | 结果 |
|---|---|
| TC 启动日志 | `Starting ServerApplication v2.6.0 using Java 17.0.12 on 192.168.5.3` |
| Nacos 注册 | `ip=192.168.5.3 port=8091 healthy=true`（旧的 `198.18.0.1` 条目已消失） |
| account 客户端 | `will connect to 192.168.5.3:8091` → `register TM success 89ms` → `register RM success 7ms` |
| account 启动 | `Started AccountExampleApplication in 5.215 seconds`（Tomcat 8102）**启动成功** |

storage 未单独复测，但它与 account 读的是 Nacos 里**同一条注册**，根因同源，已一并解决。

### 六、顺带排除的三个写法（避免再走弯路）

| 尝试 | 实测结论 |
|---|---|
| `preferred-networks: 127.0.0.1` | ❌ **无效**。回环地址在扫描阶段就被 `isValidAddress` 过滤（`FORBIDDEN_HOSTS` + `isLoopbackAddress`），根本进不了候选列表 |
| 客户端加 `-Dseata.registry.preferred-networks=10.99.*` | ❌ **不生效**。既不打印 `Could not match ip` 警告，自报 IP 仍是 `192.168.5.3` → 客户端侧**不读**该配置，只走"第一个合法地址"；该自报 IP 仅用于日志，不影响连 TC，**客户端无需改动** |
| `dubbo.consumer.provided-by`（business / order 的 yml 里） | ❌ **死配置**。Dubbo 2.7.13 的 `ConsumerConfig` / `AbstractInterfaceConfig` / `AbstractReferenceConfig` 均**无 `providedBy` 属性**（Dubbo 3.x 才引入），当前被静默忽略，不报错也无作用 |

### 七、可复用的诊断方法

出现 `can not connect to [X.X.X.X:8091]` 时，按此顺序查：

```bash
# 1. 看 TC 在 Nacos 注册的 IP（第一判据）
curl -s "http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=seata-server&groupName=SEATA_GROUP"

# 2. 看本机真实网卡 IP
ipconfig getifaddr en0          # 或 ifconfig | grep "inet "

# 3. 核对配置网段是否匹配（不匹配就会被静默回退）
grep -n "preferred-networks" <seata-server>/conf/application.yml

# 4. 复现网卡枚举顺序（纯 JDK，无需依赖）
#    遍历 NetworkInterface.getNetworkInterfaces() 打印 getName() + getIndex()
```

两个易错判据：

- **TCP 能握手 ≠ 能通信**。实测 `nc -vz 198.18.0.1 8091` 成功，但 `curl --max-time 6` 无响应 —— 代理 TUN 只接管握手，数据被吞。**别用 `nc` 通过就以为地址没问题。**
- **配置不匹配不报错**。日志里的 `Could not match ip by preferredNetworks` 是 `WARN` 级，容易被 INFO 淹没；要主动 grep。

## 问题 #002：Dubbo 2.7.13 升级到 3.3.6 过程中的三个坑

### 基本信息

| 项 | 内容 |
|---|---|
| 发现时间 | 2026-09-11 01:30 ~ 02:15 |
| 状态 | ✅ 已升级并端到端复测通过 |
| 影响范围 | 全模块：根 `pom.xml`、4 个 `application.yml`、3 个 `*DubboServiceImpl`、`TOrderServiceImpl` |
| 涉及组件 | Dubbo 2.7.13 → 3.3.6、netty 4.1.42 → 4.1.101、dubbo-filter-seata 1.0.2 → 3.3.1 |
| 动机 | 真实项目统一使用 Dubbo 3.x，学习工程同步升级以对齐版本 |
| 修复文件 | 根 `pom.xml`、`samples-*/src/main/resources/application.yml`、3 个 Dubbo 实现类 |

### 坑 1：`netty-all` 版本钉错会引入"胖包"重复类

**现象**：升级 Dubbo 3 后若仍沿用老的 `netty-all:4.1.42.Final`，classpath 上会同时存在"胖包 netty-all"和各 `netty-*` 子模块，
同名类重复；而 Dubbo 3.3.6 官方声明 netty-all 4.2.2、Seata 2.6.0 声明 4.1.101，两方版本还不一致。

**根因**（读 jar 实测）：
- `netty-all` 自 **4.1.91** 起已改为"空壳聚合器"：jar 里 **0 个类**，只是用 Maven 依赖声明把各 `netty-*` 子模块拉进来。
- `4.1.42.Final` 是旧式"胖包"：jar 里含 **2667 个类**，会与子模块产生**重复类**。
- 取 Dubbo 与 Seata 的**安全交集** `4.1.101.Final`；并逐处核实 Dubbo 3.3.6 **未使用**任何 netty 4.2 独有 API（`IoHandler` / `MultiThreadIoEventLoopGroup` 等）。

**修复**：`<netty.version>4.1.101.Final</netty.version>`。

> 结论：该版本**不可回退到 4.1.91 以下**；`netty-all` 在这里的作用只是"把子模块统一钉到 4.1.101"，它自己不带类。

### 坑 2：`dubbo.force.tag` 用方括号写法绑不进去（最隐蔽）

**现象**：为做 tag 严格隔离，给消费端配了 `dubbo.force.tag=true`，但验证时发现——把消费端 tag 设成一个**不存在的 tag**，
应用竟然**照常启动并成功调用**，隔离完全没生效。

**根因**（读字节码 + 实测）：起初用的是 Spring 惯用的方括号写法：

```yaml
dubbo:
  consumer:
    parameters:
      "[dubbo.force.tag]": "true"     # ❌ 不生效
```

`parameters` 字段定义在 `AbstractMethodConfig` 上；**Dubbo 自己的属性绑定器不会展开 `[xxx]` 这种方括号 key**
（方括号是 Spring Boot 对 `Map` 属性的宽松绑定语法，但 Dubbo 的绑定不走 Spring 那一套）。
结果消费端 URL 里**只有** `dubbo.tag=dev`、**没有** `dubbo.force.tag=true` → force 没打开 → tag 不匹配时静默回退到通用实例。

**修复**：改成**点号**形式即可：

```yaml
dubbo:
  consumer:
    parameters:
      dubbo.force.tag: "true"         # ✅ 生效
```

**验证**：启动后 grep 消费端 URL，出现 `dubbo.force.tag=true`（同时 `dubbo.tag=dev`）。
再复测：消费端 `tag=other` + `force.tag=true` → 调用时抛 `No provider available for StorageDubboService`，**隔离生效**。

### 坑 3：Dubbo 3 下"启动失败"晚 30 秒，且中途打印误导性日志

**现象**：停掉 account、单独起 order，日志先打印

```text
MigrationRuleHandler      : Succeed Migrated to APPLICATION_FIRST mode.
ReferenceConfig           : Referred dubbo service: [AccountDubboService].
DefaultApplicationDeployer: Dubbo Application[dubbo-order-example] is ready.
```

看起来**启动成功了**——但**约 30 秒后**：

```text
WARN  ReferenceConfig       : Check reference of [AccountDubboService:1.0.0] failed very beginning.
                              After 30003ms reties, finally failed.
ERROR DefaultModuleDeployer : Model start failed: java.lang.IllegalStateException:
                              Failed to check the status of the service … No provider available …
```

**根因**（反编译 `dubbo-3.3.6.jar` + 完整堆栈，非推测）：

```text
DubboDeployApplicationListener.onContextRefreshedEvent   ← 在 Spring refresh 完成【之后】才触发
  └─ DefaultModuleDeployer.startSync
       └─ DefaultModuleDeployer.checkReferences()        ← 超时 = ModuleConfig.checkReferenceTimeout
            └─ SimpleReferenceCache.check(ref, timeout)   ← 默认 30000ms（字节码 ldc2_w 30000l）
                 └─ ReferenceConfig.checkOrDestroy(timeout)
                      └─ ReferenceConfig.checkInvokerAvailable(timeout)
                           └─ while (!invoker.isAvailable() && now < deadline) Thread.sleep(100)
                                ↓ 超时
                                throw IllegalStateException("Failed to check the status of the service …")
```

要点：
1. 校验点从 2.7 的"refer 阶段"挪到了 **`onContextRefreshedEvent`**（Spring `refresh()` 末尾，**早于** Spring Boot 打印 `Started ...Application`），
   所以 Tomcat 已监听端口、Bean 已建完，日志看着像成功（实测这次全程**没有** `Started OrderExampleApplication`）；
2. `checkInvokerAvailable` 以 **100ms** 间隔轮询 `invoker.isAvailable()`，直到 **30 秒**超时才抛异常；
3. **结论不变**：provider 缺失时应用**仍然启动失败**——只是晚 30 秒，且中间那几行 `is ready` 极易被误读为成功。

> ⚠️ 我最初就被这几行 `is ready` 骗了，一度以为"Dubbo 3 不再 fail-fast"。重新做受控实验、等满 30 秒后，异常如期出现。

**修复/调优**：超时可覆盖，配置项 `dubbo.module.check-reference-timeout`（毫秒，默认 `30000`）。
设为 `0` 可恢复"立即失败"（只轮询一次，约 100ms 抛错）。

### 验证（升级后整体复测）

| 环节 | 结果 |
|---|---|
| 编译 | JDK 8 下 `mvn clean package -DskipTests` → BUILD SUCCESS |
| 4 服务启动 | 全部 `Started *ExampleApplication`，Dubbo 版本日志均为 `3.3.6` |
| `buy` 提交 | account 3200→3100、storage 500→450、t_order +1、undo_log 清空 |
| `buy2` 回滚 | 数据保持不变，undo_log 清空 |
| XID 透传 | 4 个服务日志出现**同一个** XID（`192.168.5.3:8091:…`），Dubbo 3 下 Seata 透传正常 |
| tag 隔离 | 11 次调用全部命中 `dev` 实例；`other` 实例 0 次；force.tag 下异 tag 直接 `No provider available` |
| 启动顺序 | 仍是硬性的（见坑 3），但失败延后 30 秒 |

### 可复用经验

1. **升级 Dubbo 大版本先看 netty**：`netty-all` 是否"胖包"（4.1.91 前后是两个物种），以及 Dubbo 与 Seata 声明的 netty 版本能否取交集。
2. **Dubbo 的 `parameters` 配置一律用点号，别用 Spring 的方括号**。任何 `dubbo.xxx.parameters.<key>` 同理。
   验证方式是看**消费端 URL** 里该参数有没有出现——不要只看 yml。
3. **"日志 ready ≠ 启动成功"**：Dubbo 3 的消费端校验发生在 Spring refresh 之后。
   排查启动失败时，要等到进程真正退出或出现 `Started *Application`，别被中途的 `is ready` 带偏。
4. 版本对齐清单：`dubbo-spring-boot-starter`（聚合包，勿再单独声明 `dubbo` / `dubbo-config-spring`）、
   `dubbo-registry-nacos`、`dubbo-filter-seata`（用 `org.apache.dubbo.extensions` 的 3.3.1，对齐 Seata 2.6.0 的 `org.apache.seata.*`）。

## 问题 #003：本机 IP 漂移导致 TC 与全部服务注册失效

### 基本信息

| 项 | 内容 |
|---|---|
| 发现时间 | 2026-09-11 08:50 |
| 状态 | ✅ 已修复并端到端复测 |
| 影响范围 | 全部：TC 注册 + 4 个服务的 Dubbo 注册（接口级与应用级）**全部指向失效 IP**。但**导致本次启动失败的只有 `seata-server` 那一条**，详见「三、易混淆点」 |
| 涉及组件 | seata-server 2.6.0、Nacos 2.4.3、Dubbo 3.3.6、MySQL |

### 一、现象

storage 启动即失败（`Application run failed`）：

```text
ERROR NettyClientChannelManager : 0304 register RM failed.
org.apache.seata.common.exception.FrameworkException: can not connect to services-server.
	at org.apache.seata.core.rpc.netty.NettyClientBootstrap.getNewChannel(NettyClientBootstrap.java:212)
	...
Caused by: org.apache.seata.common.exception.FrameworkException: connect failed, can not connect to services-server.

ERROR NettyClientChannelManager : 0101 can not connect to [192.168.5.3:8091] cause:[can not register RM,err:can not connect to services-server.]
WARN  ConfigServletWebServerApplicationContext : ... 'globalTransactionScanner' ... nested exception is
      FrameworkException: can not connect to [192.168.5.3:8091]
ERROR SpringApplication : Application run failed
```

**关键特征**：目标 IP 是 `192.168.5.3:8091`——**既不是虚拟网卡（198.18.x），也不是明显错值**，看起来"很正常"，
所以极易误判为"升级 Dubbo 3 弄坏了"。实际是**快失败**（连接直接失败，没有 #001 那种 30s 超时）。

### 二、根因

**本机 IP 变了，但 Nacos 里的注册 IP 是上次启动时写死的旧值。**

| 项 | 值 |
|---|---|
| 昨晚启动时本机 IP | `192.168.5.3` |
| 今晨本机 IP（`ipconfig getifaddr en0`） | **`192.168.43.156`** |
| Nacos 里 `seata-server` 注册 | `192.168.5.3:8091` ← 旧值（**启动失败的元凶**） |
| Nacos 里 4 个服务的 Dubbo 注册 | 全部 `192.168.5.3:…` ← 旧值（同样失效，但**不是**本次启动失败的原因，见「三」） |
| `nc -z 192.168.5.3 8091` | 失败（该地址在本机已不存在） |

机制与 #001 同源：TC 的注册 IP 在**启动那一刻**由 `NetUtil` 算一次写入 Nacos；Nacos 的临时实例只做心跳续命，**从不校验 IP 是否真实存在**，也不会被更新。
所以换网络后，**旧进程不停，注册就一直是错的**。

> 判据：`lsof -iTCP:8091 -sTCP:LISTEN` 显示 TC 仍在 `*:8091` 正常监听 —— **"TC 在跑"和"注册 IP 对"是两件事**。

### 三、易混淆点：两条注册，只有一条是元凶

**常见质疑：「启动失败时还没发起任何 Dubbo 调用，跟注册的 IP 有什么关系？」**

这个质疑**一半成立** —— 必须把 Nacos 里的两条注册彻底分开看：

| 注册在 | 服务名 | 谁在什么时机读它 | 与本次启动失败的关系 |
| --- | --- | --- | --- |
| `SEATA_GROUP` | `seata-server` | **Seata 客户端在启动时**读取（`GlobalTransactionScanner.afterPropertiesSet` → `NacosRegistryServiceImpl` 查 Nacos 命名服务） | ✅ **直接元凶**：查到旧 IP → 连 TC 失败 → 容器 refresh 中断退出 |
| `DEFAULT_GROUP` | `providers:…AccountDubboService:1.0.0` 等 | Dubbo 消费者在**发起调用时**才解析提供者地址 | ❌ **与本次启动失败无关**：进程还没走到 Dubbo 阶段就已经死了 |

实测时间线（同一份 account 启动日志，`grep -n` 原文）：

| # | 时刻 | 线程 | 组件 | 日志 | 所属阶段 |
| --- | --- | --- | --- | --- | --- |
| ① | 08:52:48.430 | main | `NacosRegistryServiceImpl` | *Nacos naming auth properties empty* | **Seata** |
| ② | 08:52:48.515 | main | `NettyClientChannelManager` | `will connect to 192.168.43.156:8091` ← 地址取自注册表 | **Seata** |
| ③ | 08:52:48.715 | main | `TmNettyRemotingClient` | `register TM success` | **Seata** |
| ④ | 08:52:50.125 | main | `RmNettyRemotingClient` | `register RM success` | **Seata** |
| ⑤ | 08:52:51.351 | main | `NacosRegistry`（Dubbo） | `[DUBBO] Subscribe: provider://…` | **Dubbo 首次出现** |

对应的原文行号：行 81 / 85 / 94 / 133 / 154。

**Seata 连 TC（②）比 Dubbo 第一次露面（⑤）早约 3 秒。** 所以：

- 「还没有 Dubbo 调用」→ **成立**：Dubbo 那几条注册确实不是元凶；
- 「和 Nacos 注册的 IP 没关系」→ **不成立**：`seata-server` 那条就是元凶。

**凭什么断言报错里的 IP 来自注册表**：`192.168.5.3` 在**项目的 4 个 yml 与 TC 的 `conf/` 里 `grep` 一处都不存在**；
而重启后**一个字节配置都没改**，客户端就自动连上了 `192.168.43.156:8091`（4 个服务日志一致）。
**配置里连 `8091` 这个端口都没有** —— 地址只可能来自 Nacos 的 `seata-server` 注册记录。


### 四、修复

配置**无需改动**（`preferred-networks: 192.168.*` 已能覆盖 `192.168.43.156`），只需让 TC 重新算一次 IP，并让 4 个服务重新注册：

```bash
kill <旧TC_PID> <4个服务PID>            # 全部停掉
export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home
sh bin/seata-server.sh                  # 重启 TC（JDK 9+）
# 再按顺序重启 4 个服务：account/storage → order → business
```

**注意：只重启 TC 不够**，4 个服务的 Dubbo 注册同样是旧 IP，必须一并重启。

> 补充：本次还发现 `target/*.jar` 不存在（只剩 `classes/`），需先用 JDK 8 重新 `mvn clean package -DskipTests`。

### 五、验证

| 环节 | 结果 |
|---|---|
| TC 重启后注册 | Nacos 中 `seata-server` = **`192.168.43.156:8091`**（旧的 `192.168.5.3` 条目在心跳超时后自动剔除） |
| 4 服务注册 | Account `192.168.43.156:20883`、Order `…:20880`、Storage `…:20888`，应用级注册同步更新 |
| 4 服务启动 | 全部 `Started *ExampleApplication`；`register TM/RM success` 的 channel 对端为 `192.168.43.156:8091` |
| `buy2`（回滚） | HTTP 500（预期），数据不变，TC 日志 `Rollback global transaction successfully` |
| `buy`（提交） | HTTP 200，storage 450→400、account 3100→3000、orders 9→10，TC 日志 3× `PhaseTwo_Committed` + `Committing global transaction is successfully done`，`undo_log` 归零 |
| XID 透传 | 同一串 `192.168.43.156:8091:964592193717702661` 在 4 个服务日志中一致 |

### 六、重启范围实测：TC 必须重启，业务服务不用

**问题**：「如果本机 IP 变了、TC 的注册地址也跟着变，是不是 TC 和 4 个业务服务都得重启？」

**结论**：

| 情形 | TC | 4 个业务服务 | 说明 |
| --- | --- | --- | --- |
| **本机 IP 变了**（换 Wi-Fi / 换网段） | ✅ 必须重启 | ✅ **要重启** | TC 侧见 A；业务服务是**为了修它们自己的 Dubbo 注册**（不是为 Seata） |
| **仅 TC 单方面重启**（本机 IP 未变） | ——（本身就在重启） | ❌ **不用** | 客户端 ≤10s 自动跟随，见 B |
| **开关 VPN**（LAN 网段未变） | ❌ 通常不用 | ❌ 不用 | `preferred-networks: 192.168.*` 会跳过 TUN 网卡（198.18.x / 10.x），TC 仍选 en0 |

#### A. TC 为什么必须重启 —— 没有任何热更新机制

- 注册 IP 由 `NetUtil` 在**启动那一刻**算一次，直接写进注册参数，此后不再重算；
- `seata-all-2.6.0` 的 `NetUtil` 里**没有** `register-ip` / `host` 之类直配项，**也没有**"定时重新注册"的任务；
- Nacos 临时实例只做心跳续命，**不校验 IP 是否真实存在**（#001 已证）。

→ IP 一变，注册表里就是死地址，唯一解是让进程重走一遍注册流程。

#### B. 业务服务为什么不用重启 —— 客户端 10s 周期重连，且重连时会**重新查注册表**

反编译 `NettyClientChannelManager` 得到的调用链（非推测）：

```text
doReconnect(...)            → 调 getAvailServerList(...)
getAvailServerList(...)     → RegistryFactory.getInstance().lookup(group)   ← 重新查注册表
```

周期来自 `AbstractNettyRemotingClient.init()`：

```text
scheduleAtFixedRate(runnable, 60000L, 10000L, MILLISECONDS)   // 首延迟 60s，之后每 10s 一次
```

**实测（只动 TC，4 个业务服务全程 PID 不变：68059 / 68292 / 68061 / 68492）**：

| 动作 | 观察到的结果 |
| --- | --- |
| 优雅停 TC（`SIGTERM`） | Nacos 里 `seata-server` 立即变成 `"hosts":[]` —— **优雅关闭会主动注销**（`kill -9` 才会残留死地址，见 #001） |
| 重启 TC（IP 未变） | 4 服务在 **2~9 秒**内由 `eoutChecker` 线程自动重注册 TM/RM 成功；`buy2` 仍正常回滚 |
| 停 TC + 手工往 Nacos 塞一条**假实例** `127.0.0.1:18091` | 4 服务在 **≤6 秒**内全部打印 `will connect to 127.0.0.1:18091` —— **自动跟到了新地址** |
| 删掉假实例 + 重启 TC | 4 服务又全部跟回 `192.168.43.156:8091` —— **双向都跟** |

`grep -n "will connect to"` 原始证据：

```text
svc-order.log:1254    09:55:27.070  [eoutChecker_1_1] will connect to 127.0.0.1:18091
svc-business.log:1483 09:55:30.675  [eoutChecker_1_1] will connect to 127.0.0.1:18091
svc-account.log:1443  09:55:32.377  [eoutChecker_1_1] will connect to 127.0.0.1:18091
svc-storage.log:1367  09:55:32.466  [eoutChecker_1_1] will connect to 127.0.0.1:18091
        …… 删假实例 + 重启 TC ……
svc-business.log:1630 09:55:50.673  [eoutChecker_1_1] will connect to 192.168.43.156:8091
```

> **要点**：「业务服务要重启」和「业务服务的 Seata 连接要重启」是两件事。
> 换网络时之所以要重启业务服务，是因为它们的 **Dubbo 注册**也带了探测出来的网卡 IP（机制同 §4.1），
> 那部分 **Seata 的重连机制管不着**。所以今早的修法（重启 TC + 全部服务）在**换网络场景下依然正确**，
> 只是原因要分清：**业务服务是去修 Dubbo 注册，不是去修 Seata 连接。**


### 七、可复用经验

**换网络 / 开机后，先跑这一条命令，再启动服务：**

```bash
echo "local = $(ipconfig getifaddr en0)"
curl -s "http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=seata-server&groupName=SEATA_GROUP" \
  | tr ',' '\n' | grep '"ip"'
# 两者不一致 → 重启 TC + 重启全部服务
```

三条判据：
1. **客户端报错里出现 `can not connect to [X:8091]`，且 X 是本机曾经用过的网段** → 先怀疑 IP 漂移，别怀疑代码/升级。
2. **"TC 在监听" ≠ "注册 IP 是对的"**：一定要去 Nacos 核对注册值，不要只看端口。
3. **要重启的是"TC + 所有已运行服务"**，只重启 TC 会让 Dubbo 侧继续指向旧 IP。

补一条**按报错时机区分两条注册**的判据（本次由质疑引出，详见「三」）：

| 症状 | 元凶注册 | 读取时机 |
| --- | --- | --- |
| **启动即失败**，日志含 `can not connect to [X:8091]` / `services-server` | `SEATA_GROUP` 的 `seata-server` | 启动时（Seata 初始化） |
| **启动正常，调用才报** `No provider available for the service …` | `DEFAULT_GROUP` 的 `providers:…` | 调用时（Dubbo 寻址） |

两者的共同根因都是注册 IP 陈旧，但**排查入口完全不同** —— 前者查 `seata-server` 注册，后者查 `providers:*` 注册。

> ⚠️ 补充：**"调用才报 `No provider available`" 还有另一类完全不同的成因** ——
> 提供者进程还在、端口还在监听，但注册**被整条摘除**（例如 JVM 被调试断点冻结，见 **#005**）。
> 区分点：`#003` 的注册是「**存在但 IP 陈旧**」，`#005` 的注册是「**根本不在了**（`invokers: 0[]`）」。

## 问题 #004：TC 用 JDK 8 启动 —— 客户端 `GlobalBeginRequest` RPC timeout 30s

### 基本信息

| 项 | 内容 |
|---|---|
| 发现时间 | 2026-09-11 10:11 |
| 状态 | ✅ 已修复 |
| 影响范围 | 全部：**任何**全局事务都无法开启，`buy` / `buy2` 一律失败 |
| 涉及组件 | seata-server 2.6.0（TC）、JDK 1.8（错）→ 17（对） |
| 修复文件 | `/Users/yangchao/Desktop/zhongjianjian/seata-2.6.0/seata-server/bin/seata-server.sh`（原脚本备份为同目录 `seata-server.sh.orig`） |

### 一、现象

客户端（business）日志：

```text
ERROR AbstractNettyRemoting : wait response error:null ,cost: 30009 ms,
      ip:/192.168.43.156:8091, request:GlobalBeginRequest{transactionName='dubbo-gts-seata-example', timeout=300000}
WARN  DefaultFailureHandlerImpl : Failed to begin transaction.
org.apache.seata.core.exception.TmTransactionException: RPC timeout
	at org.apache.seata.tm.DefaultTransactionManager.syncCall(DefaultTransactionManager.java:134)
	at org.apache.seata.tm.DefaultTransactionManager.begin(DefaultTransactionManager.java:89)
```

HTTP 表现：`POST /business/dubbo/buy` 挂 **30s** 后返回 500。

**最迷惑的地方**：TC 这一侧"看起来一切正常"——

- 进程在跑，`lsof -iTCP:8091` 正常 LISTEN
- Nacos 里 `seata-server` 注册 `healthy=true`
- TC 启动日志有 `Starting ServerApplication ... Server started, service listen port: 8091`

只有 `~/logs/seata/seata-server.8091.error.log` 里才藏着真相。

### 二、根因

这次是**用户自己**用 `sh bin/seata-server.sh` 重启的 TC。该脚本走 `seata-setup.sh`，在没有显式指定时按环境变量 `JAVA_HOME` 选 java —— 而用户终端里的 `JAVA_HOME` 指向 `jdk-1.8`，于是 TC 跑在了 JDK 8 上。

Seata 2.6.0 server 的编码路径 `GlobalSession.encode` 调用 `java.nio.ByteBuffer.clear()`。
该方法自 **JDK 9** 起把返回类型由 `Buffer` 收窄为 `ByteBuffer`（协变返回类型）。
JDK 8 下编译出的调用签名是 `clear()Ljava/nio/Buffer;`，于是在 JDK 8 上运行 TC 时抛：

```text
java.lang.NoSuchMethodError: java.nio.ByteBuffer.clear()Ljava/nio/ByteBuffer;
	at org.apache.seata.server.session.GlobalSession.encode(GlobalSession.java:646)
	at org.apache.seata.server.storage.file.TransactionWriteStore.encode(TransactionWriteStore.java:89)
	at org.apache.seata.server.storage.file.store.FileTransactionStoreManager.writeSession(FileTransactionStoreManager.java:183)
	at org.apache.seata.server.session.AbstractSessionManager.addGlobalSession(AbstractSessionManager.java:77)
	at org.apache.seata.server.coordinator.DefaultCore.begin(DefaultCore.java:228)
	at org.apache.seata.server.coordinator.DefaultCoordinator.doGlobalBegin(DefaultCoordinator.java:323)
	at org.apache.seata.server.AbstractTCInboundHandler$1.execute(AbstractTCInboundHandler.java:66)
	at org.apache.seata.core.protocol.transaction.GlobalBeginRequest.handle(GlobalBeginRequest.java:75)
```

TC 的 `ServerOnRequestProcessor` 把异常吞在 `error.log` 里，**不回 `GlobalBeginResponse`** ——
对客户端来说就是"发出去石沉大海"，只能等满 30s 超时。

**三条判据（30 秒内确认是不是这个坑）**：

```bash
# ① TC 进程实际跑的 java 是哪个版本
P=$(lsof -ti tcp:8091 -sTCP:LISTEN | head -1)
lsof -p "$P" | awk '$4=="txt"' | grep -oE "/[^ ]*jdk[^ ]*/bin/java" | head -1

# ② TC 启动日志里的 Java 版本
grep "Starting ServerApplication" ~/logs/seata/seata-server.8091.all.log | tail -1
#    → 出现 using Java 1.8 即中招

# ③ 错误日志里有没有这条 NoSuchMethodError
grep -c NoSuchMethodError ~/logs/seata/seata-server.8091.error.log
```

### 三、修复

**根治办法：把 JDK 钉进启动脚本，而不是靠每次 `export JAVA_HOME`。**

改动 `bin/seata-server.sh`，在 `. ${BASEDIR}/bin/seata-setup.sh` **之前**插入：

```bash
SEATA_JAVA_HOME="/Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home"
if [ ! -x "${SEATA_JAVA_HOME}/bin/java" ] ; then
  if [ -x /usr/libexec/java_home ] ; then
    SEATA_JAVA_HOME="$(/usr/libexec/java_home -v 17 2>/dev/null)"
  fi
fi
if [ ! -x "${SEATA_JAVA_HOME}/bin/java" ] ; then
  echo "Error: 未找到 JDK 17，Seata Server 2.x 必须用 JDK 9+ 启动。" 1>&2
  exit 1
fi
if [ -n "${JAVA_HOME:-}" ] && [ "${JAVA_HOME}" != "${SEATA_JAVA_HOME}" ] ; then
  echo "[INFO] 已忽略环境变量 JAVA_HOME=${JAVA_HOME}"
fi
export JAVA_HOME="${SEATA_JAVA_HOME}"
export JAVACMD="${JAVA_HOME}/bin/java"
echo "[INFO] 使用 JDK: ${JAVA_HOME}"
```

**为什么必须放在 `source` 之前（这是本次改动最容易做错的地方）**：
`seata-setup.sh` 依据 `JAVACMD` 的版本**生成 GC 参数**——

```text
JAVA_MAJOR_VERSION=$(... "$JAVACMD" -version ...)
if [ "$JAVA_MAJOR_VERSION" -ge 9 ]; then
  JAVA_OPT="$JAVA_OPT -Xlog:gc*:file=..."       # JDK9+
else
  JAVA_OPT="$JAVA_OPT -Xloggc:... -UseG1GC"     # JDK8
fi
```

所以若只在 `source` 之后覆盖 `JAVACMD`，就会变成「**JDK 17 在跑 + JDK 8 的 GC 参数**」的错配。
放在 source 之前，版本探测才会看到 JDK 17。

### 四、验证

| 验证点 | 结果 |
| --- | --- |
| 启动脚本输出 | `[INFO] 使用 JDK: /Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home` |
| 命令行 GC 参数 | 由 `-Xloggc:...` 变为 **`-Xlog:gc*:file=...`**（证明版本探测走对了分支） |
| TC 启动日志 | `Starting ServerApplication v2.6.0 using **Java 17.0.12**` |
| `GlobalBeginRequest` 响应 | `10:17:37.889` 收到 → `10:17:37.905` 回 `GlobalBeginResponse`，**16ms**（此前是 30s 超时） |
| `NoSuchMethodError` 计数 | 重启后为 **0** |
| 业务链路 | `buy` 提交（storage 400→350、account 3000→2900、orders 10→11）；`buy2` 回滚（0.028s、数据不变） |

### 五、可复用经验

1. **"TC 在监听 + Nacos healthy" ≠ "TC 可用"**。这个坑里三项表象全部正常，唯一异常藏在 `seata-server.*.error.log`。
   排查"客户端 RPC timeout"时**必须同时看 TC 侧的 error 日志**，只看客户端会一直以为是网络/注册问题。
2. **TC 与客户端的 JDK 要求不同**：**server 端必须 JDK 9+**（本例 17），
   而客户端 `seata-spring-boot-starter` 在 JDK 8 上工作正常 —— 不要"因为客户端用 8"就以为 server 也能用 8。
3. **凡是"启动脚本按环境变量挑 JDK"的工具链**，都把版本钉在脚本里。
   靠人工 `export` 迟早会在某次换终端 / 换 IDE 终端时失效，而且失效后的报错完全不像 JDK 问题。

| 检查 | 结果 |
| --- | --- |
| Nacos 服务名是否还在 | 在 —— `providers:…StorageDubboService:1.0.0:` 与 `dubbo-storage-example` 都列得出来 |
| Nacos 实例列表 | **一个都没有**（接口级与应用级同时为空） |
| storage 进程 | **还在**，`lsof` 显示 8109 / 20888 都在 LISTEN |
| `curl http://127.0.0.1:8109/` | **`HTTP=000`**（TCP 能连上，应用层不响应） |
| 另一次现象 | 某个 `buy2` 卡了 **53 秒**才失败，报 `Channel org.apache.dubbo...NettyClient [... -> /192.168.43.156:20888] is inactive` |

### 二、根因

storage 是以 **Debug 模式**启动的，`TStorageServiceImpl.decreaseStorage`（`TStorageServiceImpl.java:24`）上留着断点。
IDEA 默认挂起策略是 **suspend = All**，断点一命中就冻结**整个 JVM**（不只是命中的那一个线程），于是连锁反应：

- **Nacos 客户端心跳线程**停发 → 约 **15s** 后实例被判定超时摘除（接口级 + 应用级一起没了）
- **Tomcat 线程池**不再响应 → `HTTP=000`
- 此前已建立的 **Dubbo 连接**被判定 `is inactive`

直接证据 —— `jstack <storage pid>`：

```text
"DubboServerHandler-192.168.43.156:20888-thread-7" #2117 daemon prio=5 os_prio=31
    tid=0x00000001227b8800 nid=0x2cd07 **at breakpoint**[0x0000000318b28000]
   java.lang.Thread.State: RUNNABLE
	at io.seata.samples.integration.storage.service.TStorageServiceImpl.decreaseStorage(TStorageServiceImpl.java:24)
	at ...TStorageServiceImpl$$FastClassBySpringCGLIB$$29699009.invoke(<generated>)
	at org.springframework.aop.framework.CglibAopProxy$DynamicAdvisedInterceptor.intercept(CglibAopProxy.java:685)
	at io.seata.samples.integration.storage.dubbo.StorageDubboServiceImpl.decreaseStorage(StorageDubboServiceImpl.java:30)
	...
```

注意线程状态写的是 `RUNNABLE` —— **没有 BLOCKED、没有死锁**，光看状态列会漏掉；
真正的标志是行尾那个 **`at breakpoint`**。

### 三、修复

在 IDE 里**取消该断点**，或点 **Resume / Continue**；要避免复发就用 **Run** 模式而不是 Debug 模式启动。

### 四、验证

| 验证点 | 断点命中期间 | 放行之后 |
| --- | --- | --- |
| `curl http://127.0.0.1:8109/` | `HTTP=000` | `HTTP=404`（应用恢复响应） |
| Nacos 接口级注册 | 无实例 | `192.168.43.156:20888` `healthy=true` |
| Nacos 应用级注册 | 无实例 | `healthy=true` |
| `buy2` | 卡 53s 后失败 | **0.028s** 正常回滚、数据不变 |

### 五、可复用经验

1. **一条判据定位**：**「进程还在 + 端口 LISTEN + 应用不响应（curl 返回 `000`）+ 注册凭空消失」**
   → 立刻 `jstack <pid> | grep -n "at breakpoint"`。这比先查 Nacos、再查 Tomcat、再翻日志快得多。
2. **`HTTP=000` 与 `HTTP=404` 要分清**：`404` 说明**应用活着**（只是没这个路由）；`000` 说明**应用层不响应**
   （或连接层根本没通）。前者不用管，后者才是故障信号。
3. **调试 Dubbo provider 时命中断点会"连坐"**：注册消失、别的服务调用失败、Seata 事务超时回滚，
   表面上像三四个孤立问题，实际只有一个断点。排查时优先找**被冻结的那一个**。
4. `jstack` 里 `Thread.State: RUNNABLE` **不代表线程在干活** —— 命中断点时状态仍显示 RUNNABLE，
   必须看行尾的 `at breakpoint` 标记。
